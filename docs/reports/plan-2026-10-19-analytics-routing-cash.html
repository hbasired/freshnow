3. Rules that hold throughout

  • The model never computes a number. Every figure on a dashboard comes from SQL; insights are fixed sentences filled from query results (CLAUDE.md rule 2). Optional wording by the model passes the numeric gate.
  • Deterministic, replayable jobs. Every analytics run, forecast, route and audit stores its inputs, parameters and output, so it can be run again and give the same answer (rule 3).
  • Machines and processes are scored — never people. Driver–region patterns (R3) are used to suggest assignments, never to rank anyone (CLAUDE.md "do not build employee ranking").
  • Televend stays read-only until you decide otherwise per operation (Q13); the bridge account never writes.
  • Every task follows the loop: research → plan → build → verify → document (HTML + knowledge base), with what was not verified.

5. How the hard parts work

5.1 Analytics (070, 071, 075)

  • Cups per day = a machine's sales ÷ the days in the range it was live; the fleet average is the mean over live machines with any sale. Machines with no sale for two days or more are listed apart ("check them"), not averaged in.
  • Tiers (Q2) and the 80 % set (the fewest machines making 80 % of cups). Category per machine-day makes a category of 19 machines comparable with one of 2.
  • Same day last week: each day is compared with the same weekday 7 days earlier — never with the day before (weekday patterns).
  • Insights are fixed sentences filled from SQL — e.g. "Hospital / Clinics: 19 machines, 38 % of cups, 41 cups per machine per day — the highest category" — with the query behind each number shown on demand. Actions are rules with evidence: "No sales for 2 days at Burjuman 312 — check the machine".
  • The store (071): aggregates per machine per day and hour carry no personal data and are kept; each nightly run records the last sale it saw, so it can be replayed.

5.2 Alarms that clear themselves (074)

Some alarms are proven over by a sale (a vend failure, a cup or coin fault, a lost connection): if a sale succeeds on the same machine after the alarm began, we mark it cleared by the next sale, with that sale as the evidence; others (product low, cash box full) are never cleared this way. Over 28 days each alarm type on each machine gets a share cleared by itself; above the threshold it is "likely false" — still recorded and listed, never sent as an alert, and reviewable by the Ops Head. Televend is not changed.

5.3 The MCP ↔ API switch (082) — built so it cannot mix sources

  • Names in .env, empty until you paste them: TELEVEND_CLIENT_ID, TELEVEND_CLIENT_SECRET (exist since TASK-055), plus TELEVEND_API_KEY (if Televend's gateway issues one), TELEVEND_API_BASE_URL, TELEVEND_AUTH_URL, TELEVEND_COMMIT_OFFSETS. "MCP" today means the bridge: our connector signed in as your Televend user, sending only allow-listed reads; the MCP tools use the same connector, so they follow the switch.
  • One source of truth: the live source is one row in the database, changed only by the CEO or an Admin with a typed confirmation, audited (who, when, from what to what).
  • Four states: bridge (now) → API shadow (both read; the API's data is compared with the bridge's, the bridge stays the source) → API (the API is the source; the bridge stops) → fall-back to bridge automatically after 30 minutes of API failures, with an alert. "API" is offered only after the key passes a live test and the shadow week shows matching totals.
  • No double counting: every copied row carries its source and Televend's own id; the same sale from both sources is one row. Streams keep 7 days, so the switch-over overlaps and the unique keys absorb the overlap.

5.4 Writing to Televend (083 — only if you say yes)

Your rule since 15 Oct is read-only, to protect Televend's logging and balance tally; your new message expects the API to be used "for reading, writing". Both are honoured by keeping writes off until you turn on one operation at a time, after Televend confirms the endpoint: off → dry run (built and logged, not sent) for two weeks → on; each write has an idempotency key and is confirmed by reading Televend back. The bridge account never writes. If Televend offers no write endpoint, the Staff App stays for Televend's own records and our app sends nothing there.

5.5 Routes (078–081)

Inputs: machine and warehouse locations (pins or Google Maps links), Televend's stock figure and the forecast, service rules (night-only), shifts, people and their usual regions, van capacity in crates, travel times from OSRM. Solver: VROOM (open source, built for vehicle routing with capacities and time windows, on OSRM) — or OR-Tools — with fixed settings, a solution limit instead of a time limit, one thread, so the same inputs give the same routes; ant-colony optimisation as a benchmark (Q10). Output: draft Route plans with the reason for each stop ("stock 23 %, forecast 41 cups by 18:00") and the cartons, parts and consumables per person, computed at 00:00; the Supervisor reviews; each person receives theirs one hour before their shift (Q11). Audit: each run stores inputs, solver and version, settings and output; a replay test runs it again.

5.6 OCR (068)

PaddleOCR's text recognition (PP-OCRv5) on our server reads the photo; fixed parsers per kind of paper turn the text into fields (the deposit slip's amount, date, transaction number and notes; a fuel receipt's amount and litres; the counter on the machine's screen). The form is filled as a proposal with each field marked; the person corrects and saves; a number that is not in the text is never filled. Accuracy is measured on your real photos before it is switched on (Q8).
