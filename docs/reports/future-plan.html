What to build next

FreshNow Operations Platform · 18 September 2026 · written after a full audit of the running system and a review of how comparable production systems are actually built

The headline answer on RAG: not yet, and not for the operational data — probably never for that part. The system's operational data is structured, and for structured data a semantic layer with text-to-SQL beats retrieval, because a query computes an exact answer over every row while retrieval returns whatever looked similar. That architecture is already built here and working.

RAG becomes the right tool the moment FreshNow hands over its documents — HACCP plans, equipment manuals, supplier contracts, the food-safety code. Those are unstructured, they are what people actually need answers from, and nothing in the current design can touch them. That is the trigger to watch for, and it is a question to ask the company rather than a date to put in a plan.

1 · Why RAG is the wrong tool for the data we have today

The measurement that settles it

Queried against the live database on 18 September 2026:

  • 7 rows of employee free text (task_update.note_raw)
  • Average length: 28 characters. "van 2 ka chiller theek nahi hai" is a typical one.
  • 0 stored documents.

There is no corpus. A retrieval system over 7 short sentences is not a retrieval system; it is a WHERE clause with a vector index bolted on, and it would be slower, less accurate and less explainable than the SQL that already answers those questions.

The structural argument, independent of size

Even at a thousand times the volume, the operational data would be the wrong shape for RAG. The current industry consensus is unambiguous on this split: use retrieval for unstructured text, and a semantic layer with text-to-SQL for structured data — because text-to-SQL guarantees an exact match from database fields rather than depending on finding something semantically similar, and it reads live data with no re-indexing.

That is precisely what this system already does, and it is the architecture CLAUDE.md commits to in its second rule — "the LLM translates; the engine computes":

natural language → [model: translate] → SQL
                                          ↓
                    [Postgres: compute exactly, over every row]
                                          ↓
              answer ← [model: narrate] ← ≤ 50 rows

Ask "how many blockers are open right now" and the current design counts them. A RAG design retrieves some blocker records and asks a model to count what it was handed — which is the single failure mode HONESTY-AND-ACCURACY.md exists to prevent. Replacing SQL with retrieval here would be a downgrade dressed as an upgrade.

2 · When RAG becomes right — the trigger conditions

Build it when any two of these are true, not before:

  1. FreshNow hands over its document set — HACCP plan, SOPs, equipment manuals, supplier contracts, the Dubai Municipality Food Code sections that apply. This is the strongest trigger on its own.
  2. Employee free text passes roughly 5,000 entries and people start asking "has this happened before?" — a question SQL answers badly and retrieval answers well.
  3. Somebody asks a question no table can answer — "what does the manual say to do when the filler head jams?" There is no column for that.

Until then, every hour spent on retrieval is an hour not spent on the routing table, the reporting lines, or food-safety records — all of which are worth more.

What a correct RAG build would look like here

Recorded now so it is designed rather than improvised later. Current production practice has converged on a multi-stage retrieval pipeline rather than naive embed-and-search:

DecisionWhat and why
Storepgvector in the Postgres we already run — confirmed installed and available. No new container, no new vendor, no second source of truth, and retrieval can be filtered by the same RLS-scoped tables in one query. A dedicated vector database is not earned at this scale.
Hybrid retrievalVector plus keyword search, not vector alone. Combining the two is reported to improve retrieval accuracy by roughly 15–25% in production deployments, and keyword search is what catches the exact part number or batch code that semantic similarity misses.
RerankingA cross-encoder pass over the top candidates. Raw vector similarity retrieves documents that are topically related but contextually wrong — this is named as one of the four structural causes of RAG failure in production.
ChunkingStructure-aware, never fixed-size. Fixed-size chunking on mixed document types splits semantic meaning across boundaries and destroys retrieval quality at scale. An SOP's steps must not be cut in half.
Access controlFilter at retrieval, and verify every cited chunk after. This is the single most important security control for enterprise RAG. It maps directly onto the RLS model already in place — and given the audit found the question box running as a BYPASSRLS role, this system has already learned that lesson once.
CitationsEvery claim cites a source document and section. This also finally implements the grounding gate that CLAUDE.md specifies and that is currently not built.
EvaluationA fixed question set, scored on every change. Retrieval that worked on day one degrades silently as the corpus grows; without continuous evaluation you find out when somebody complains. Langfuse is already wired and would carry this.
Embedding modelPin it, and treat a change as a full re-index. Switching embedding models without re-indexing corrupts similarity scores — a documented way to break a working system invisibly.

Rough size: two to three weeks once documents exist. Roughly a third of that is ingestion and chunking, a third retrieval and reranking, a third evaluation — and the evaluation third is the one usually skipped and the one that determines whether it still works in six months.

3 · The plan, in the order it should happen

NOW Close what the audit found

An adversarial audit on 18 September found six critical items. Three are already fixed (see §4); the rest belong at the front of any plan because they are correctness and safety, not features.

  1. Replay does not replay. It re-reads live mutable state instead of the recorded inputs, so 90% of real runs report "diverged" — and a nonexistent run reports "no divergence". Store the inputs in the audit detail and replay from those.
  2. The observability spine is written only by the seeder. run_trace has two rows, both from seed.ts. No production path writes it, so "every run is reconstructible" is not true today.
  3. A routing failure loses a blocker permanently. If routing throws, the blocker exists with no resolver and no SLA, and the sweep filters those out — nobody is ever told. Needs a catch and a reconciliation query for unrouted blockers.
  4. Abandoned messages vanish silently. Five delivery attempts, then a console line and nothing else — including for escalation alerts to the CEO.
  5. No correlation id on the outbox or escalation tables, so the message a person actually receives cannot be traced back to the run that produced it.

1 Make it FreshNow's system rather than a demo (needs the company)

Gated on docs/WHAT-WE-NEED-FROM-FRESHNOW.md. Nothing here is hard; all of it is blocked on answers.

  • Real reporting lines, roles, departments — the highest-leverage single input
  • The real routing table, and the code change to read site and shift (currently ignored)
  • Real SLA windows and escalation rungs, including whether they run out of hours
  • Remove the hardcoded demo CEO id from the escalation ladder and the audit actor
  • Consent for everyone already in the system, and a check before capture

2 Production deployment

  • Telegram webhook mode and its secret-token check. Neither exists — the bot only long-polls. This is presented in DEVIATIONS.md as a configuration switch; it is a code change, and the audit was right to call that out.
  • Caddy, TLS, a domain
  • Retention and erasure (PDPL requires it; currently not built at all)
  • Backups, and a restore actually tested
  • Uptime monitoring, and a /health that checks Redis and Telegram rather than only Postgres

3 Food safety — the largest unbuilt opportunity

FreshNow produces juice in Dubai under HACCP obligations, and Dubai Municipality now runs a digital food-safety platform that inspectors check on every visit. The platform records none of this.

  • Critical control points, their limits, and who is told when one is breached — reusing the existing alerting machinery, which is exactly what it is for
  • Temperature and cooling logs against the published rules (≤ 5 °C storage; 60 °C → 5 °C within 6 hours)
  • Batch and lot traceability, already sketched in the Phase 3 specification
  • Retention to whatever period the inspector requires

Deliberately not built speculatively. A temperature log that does not match how you are actually inspected is worse than none.

4 RAG over documents — only once documents exist

As designed in §2. The trigger is the document set arriving, not a date.

5 Vending telemetry

Standing recommendation unchanged: check whether Nayax or Vendekin expose an API before building anything. Buying is the recommended path; building telemetry from scratch is a project in its own right.

4 · What was fixed today, in response to the audit

FindingFix
The question box ran model-written SQL as a BYPASSRLS role that can read auth.users — password hashes and refresh tokens. CLAUDE.md claimed it used "a read-only role against pre-approved views"; neither half was true.Now runs as the RLS-enforced app role inside the asker's own context — that role has no privileges on the auth schema at all. Plus a schema and catalogue denylist in the guard, with 11 tests.
An employee could promote themselves to CEO at the RLS layer — the UPDATE policy had no column restriction.Migration 0014 adds a trigger refusing changes to access_role, auth_user_id, manager_employee_id, department, status and telegram_user_id from anyone but the CEO or the service role. Verified as the real app role: blocked, while ordinary profile edits still work.
Routing was not deterministic — no uniqueness on routing_rule, so duplicate rules made the winner arbitrary.Unique index on (category, site, shift), NULLS NOT DISTINCT.
The semantic-layer test checked table names only, so a documented column that did not exist and four real columns that were undocumented all passed.Now checks every column in both directions. It immediately caught schema_migrations.filename (the real column is name), a phantom project_member.is_synthetic, and employee.role_title — the column a model most easily confuses with access_role.
Six unindexed foreign keys on hot paths, including escalation.blocker_id, joined every 60 seconds by the SLA sweep.Indexed.

What we have not verified

  • The RAG recommendation is an architectural judgement, not a benchmark. Nobody has built both and measured them on FreshNow's data — because FreshNow's document data does not exist yet. The reasoning rests on the structured-versus-unstructured split and on the current corpus being 7 rows.
  • The 15–25% hybrid-retrieval figure is quoted from published practice, not measured here.
  • Effort estimates are rough and assume the documents arrive in a readable form. Scanned PDFs needing OCR would change them materially.
  • The audit's remaining findings are recorded, not fixed — replay, run_trace, the routing-failure path, abandoned-message alerting and the missing correlation ids are all still open.
  • The food-safety section assumes the published Dubai Municipality rules apply as written. Nobody has confirmed with an inspector which specific records FreshNow is held to.
  • No load testing at any point. Every "this scales" claim in this document is reasoning, not measurement.
