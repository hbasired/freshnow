TASK-009 — Routing & Escalation Engine

Phase 1 (demo) · 2026-09-04 · Satisfies SPEC-000 R4–R6 (deterministic routing & escalation) and R20 (the model never decides who resolves or whether to escalate) · The rules-based heart of the demo. 47/47 tests green (8 routing rules + 2 BullMQ, real Redis).

What was done

  • packages/core/src/routing.ts — routeBlocker (table lookup → resolver + SLA), routeAndAlert (route + enqueue one CEO alert), escalateBlocker (level+1, one alert per level), acknowledgeBlocker, slaSweep (safety net), slaMinutesFor.
  • packages/worker/src/escalation.ts — BullMQ armEscalation/cancelEscalation (delayed job keyed by blocker id) and a worker that escalates only if the blocker is still open.
  • worker/src/index.ts — the loop now runs the outbox relay, the escalation worker, and a periodic slaSweep.
  • Tests — 8 rule tests (per-severity SLA, category routing, catch-all, idempotent alert, escalation levels, ack, sweep) and 2 BullMQ arm/cancel tests against real Redis.

Why it was done

Routing is a table lookup, not a model call. When the CEO asks "why did this go to X?", the answer is a routing_rule row — reproducible and auditable. The LLM said what kind of problem it is (Task 008); a lookup decides who gets it. In the demo every rule resolves to the CEO, but the engine is table-driven, so real multi-resolver routing is a data change, not a rewrite.

Escalation is a rule on severity + age + SLA. Same inputs, same decision. The delayed job is a BullMQ job — "escalate in N minutes unless acknowledged" survives a restart, which a setTimeout would not. The slaSweep is a belt-and-braces safety net if a timer is ever lost.

How it works

routeAndAlert(blockerId)
  routeBlocker: lookup routing_rule (category + catch-all, most specific first) → CEO
               set assigned_resolver + sla_due_at = now + SLA(severity)
               audit "blocker.routed"
  enqueue ONE outbox alert to the resolver (idempotency: blocker-alert-<id>)

armEscalation(blockerId, delayMs)  →  BullMQ delayed job (jobId esc-<id>)
  fires → still open? → escalateBlocker (level+1, alert, audit)
  acknowledged? → cancelEscalation removes the job

slaSweep (every 5 min) → open + past sla_due_at + never escalated → escalateBlocker

SLA windows (minutes): critical 15 · high 60 · medium 240 · low 1440. These are placeholders until the company supplies real ones.

Concepts and techniques used

  • Deterministic routing — a lookup keyed by (category, site, shift); the demo uses category + catch-all.
  • Delayed jobs vs setTimeout — BullMQ persists the timer in Redis, surviving restarts.
  • jobId as idempotency + cancel handle — arming twice is a no-op; cancelling is one remove.
  • Safety-net sweep — a periodic query catches anything a lost timer missed.
  • Bounded escalation — levels increment from stored state; never an unbounded loop.
  • Idempotent alerts — one outbox row per blocker (and per escalation level).

Research findings

Reused the transactional-outbox and BullMQ research. New gotcha: BullMQ 6 needs ioredis installed explicitly (it is an optional peer that pnpm does not auto-install) — otherwise the queue throws "could not load the optional 'ioredis' package".

What we have not verified

  • SLA windows are ASSUMED placeholders (critical 15 / high 60 / medium 240 / low 1440 min). Real values await company answer A9.
  • The delayed job FIRING is not tested for timing — only arm/cancel are (waiting 60 s in a test is flaky). The escalation action is tested via slaSweep and direct calls; the BullMQ fire→process path is trusted, not measured.
  • Routing ignores site/shift — the blocker carries only category; site/shift live on routing_rule for future org-wide routing and would be derived from the raising employee then.
  • The CEO alert's chatId is NULL until the CEO links their Telegram id (Task 007), so alerts enqueue but cannot deliver yet.
  • No load/soak testing of the sweep or the queue.
