TASK-043 — Four channels, three switches, and a web push that really sent

2026-09-19 · migration 0017 · core: channels.ts, push.ts, inbound-email.ts · worker: three new senders · dashboard: PWA + two cards · 412 tests passing (from 376), 4 failing for an unrelated provider outage

One-sentence summary: The in-app inbox, web push, email (both directions) and a company-chat webhook are all built and wired to switches the CEO controls — every one of them shipped off, with Telegram untouched as the live channel — and web push was proven end to end by sending a real encrypted notification to Microsoft's push service and getting it accepted.

1 · What was already there, and what was actually missing

Migration 0011_alerting.sql was written for this: notification_outbox.channel already allowed telegram | inapp | email | webpush, the worker's Senders map was already keyed by channel, and a row whose channel has no sender is simply never claimed — so an unfinished channel was inert rather than broken. The idempotency key already ended in :<channel>.

What was missing was not delivery but control: a channel was on if an environment variable said so, which is a developer's decision made in a file the company cannot see. And the in-app channel was already finished — inAppSender is a deliberate no-op because the row is the notification.

2 · Three switches, not one

A message now needs all three of these to be true, and they belong to three different people:

GateWhose decisionWhere it lives
Available — are the keys on this box?a developer.env, read by channelAvailability()
Enabled — is the company using it?the CEOchannel_setting, flipped in the dashboard, audited as channel.toggled
Preferred — does this person want it?each employeenotification_pref (already existed; opt-in for everything but Telegram)

The reason they are separate is the error message. "Web push is not configured on this server" and "the company has not switched web push on" are different problems with different fixes, and the Channels card says which — a toggle that silently does nothing is worse than one that explains itself.

A hole this closed

Four call sites queued a channel directly and never consulted any gate: updates.ts:288 (needs-review), :432 (attachments), projects.ts:491,500. Once a CEO could switch Telegram off, those four would have kept posting to it. Fixed in one place — enqueueNotification now drops a message on a channel that is not live and audits notification.channel_disabled — rather than in four places that can drift apart. The audit row carries the channel and the recipient, never the message body.

Inbound email is the dangerous one, and is treated that way

It is the only path where something outside the company can cause a write, and anyone can put any address in a From: header. Five gates, cheapest first: a constant-time shared secret; SPF, DKIM and DMARC must all pass (a missing verdict is treated as failing — an edge that did not check is not evidence); the sender must be an active employee who may give work; auto-replies and bulk mail are dropped; and even then the result is a proposal a human confirms, never a silent write. Every refusal is audited with the reason and never the body. With no secret configured the route returns 404 — an unconfigured write path that works is worse than one that does not exist.

Two things that went wrong, recorded rather than tidied away

My own browser harness flipped the wrong switch. After enabling Email, a toast shifted the layout by one row and the "put it back" click landed on Telegram, switching the live channel off on the real database. Nothing was lost and no message was missed, and I found it in seconds because channel.toggled records who and what — the audit log did exactly the job it exists for. The toggles now carry a stable aria-label and data-channel so a test can address them by identity rather than position.

Groq is timing out at 25 s per call and OpenRouter is silently absorbing the traffic — visible in llm_call as ok=false, 25058ms followed by openrouter ok=true. The fallback chain is behaving exactly as designed. It is also a live demonstration of the residency problem already flagged: employee text is now reaching a second US provider with nobody being told. Four tests that make real model calls exceed their 30 s timeout because of it; they are unrelated to this work and passed earlier the same day.

What we have not verified

  • Web push has never reached a phone, and cannot until there is a domain: service workers only run in a secure context, so http://10.205.60.148:3001 is dead ground. Localhost proves the whole pipeline; iOS additionally requires Add to Home Screen, which nobody has done here.
  • No notification has been seen by a human. Microsoft accepted the encrypted payload; whether a banner appeared on a screen was not observed, because the browser had closed.
  • Email has never sent a message. The sender is tested against an injected transport, not an SMTP server — no provider account exists, no domain, no SPF/DKIM/DMARC. Deliverability is completely unproven.
  • Inbound email has never received one. The five gates are tested with fixtures; no Cloudflare Email Worker has been written or deployed, and the Worker script itself is not in this repo.
  • The chat sender has never spoken to Mattermost — only to a local HTTP server. The compose file has never been started.
  • Encryption and HTTP transport for push are not covered by our tests, by design: that boundary is injected so the sender's own decisions could be tested, and it belongs to web-push.
  • Nobody has tested a hard bounce for real, so the "turn email off for that person" rule is proven only against a synthesised 550.
  • employee.email exists but no address has been stored, and the consent notice still does not mention email — which it must before one is.
