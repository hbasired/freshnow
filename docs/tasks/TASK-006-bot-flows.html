Why it was done

The demo's whole purpose is to show a company official a working loop on a real phone. Every part of that loop existed except the surface people actually touch.

The onboarding design — and the rule it had to respect

05-TELEGRAM-DATA-FLOW.md §3 is explicit: never let someone self-declare who they are, because anyone who finds the bot could enrol as anyone. But the requirement was equally explicit that the CEO must not do data entry for every employee. These are reconciled by splitting identity from description:

CEO types a NAME only  ──►  single-use code (72h)  ──►  employee redeems it
                                                            │
                                        consent shown BEFORE the code is consumed
                                                            │
                            code + consent accepted ──► employee row created & linked
                                                            │
                              employee self-fills department / role / site / shift

The code is the authorisation gate (spec-faithful); the descriptive profile is self-filled (as required). Checking a code does not consume it, so consent is genuinely obtained before anything is written.

How it works

Ordering that protects the employee's words

Tapping Blocker writes the task_update row immediately with the button status — which is deterministic ground truth — and no note. The bot then asks what's blocking it. When the text arrives it is written to note_raw and the employee is acknowledged before the model is called. Only then does parse → route → alert run. If Groq is down the update is flagged needs_review and the employee's words are still on disk (SPEC-000 R23).

Conversation state

A small tagged union in grammY's in-memory session (awaiting_code | awaiting_consent | profile | blocker_note | new_task | invite_name | assign_title). A restart loses only the pointer to the next question, never data, because each answer is written to Postgres as it arrives.

Nothing is sent directly

Assignment and alerts both write to notification_outbox with an idempotency key; the worker delivers. The CEO's alert carries an Acknowledge button whose tap cancels the escalation timer — an explicit human action, never autonomous (SPEC-000 R21).

Concepts and techniques used

  • Thin adapter / fat core — every handler is translate-and-delegate, so the logic is unit-testable without a Telegram harness (CLAUDE.md rule 1).
  • Authorisation gate vs. descriptive data — the security-relevant fact (who you are) is granted; the non-sensitive facts (what you do) are self-declared.
  • Consent-before-write, with a notice hash — proves what was agreed to, not merely that something was.
  • Transactional redemption with SELECT … FOR UPDATE — a double redeem cannot create two identities.
  • Write-raw-first — persistence ordering as a durability guarantee.
  • Column whitelisting — the profile updater switches over a fixed field set; an SQL identifier is never built from input.
  • Transactional outbox — assignment/alert delivery survives restarts and is exactly-once.

Research findings

  • Bot token verified live against getMe: the bot is @freshnow1bot. getWebhookInfo returned an empty URL, so long polling runs without the webhook/polling conflict.
  • grammY session ships in core grammy (no extra dependency); the conversations plugin was not needed for a 7-state machine.
  • callback_data 64-byte limit — the longest payload used is log:<uuid>:blocker at 48 bytes, comfortably inside the cap.
  • Correction carried forward: the LLM provider is Groq (api.groq.com, gpt-oss-120b) with an NVIDIA NIM fallback — not xAI's "Grok". Earlier planning notes said xAI; the code was already correct.

What we have not verified

  • No flow has been exercised on a real phone yet. Every handler is covered indirectly through its core function, but the actual tap-through (buttons rendering, force-reply behaviour, message ordering) is untested until the two accounts run it. This is the single biggest gap.
  • CEO_TELEGRAM_USER_ID is still empty, so resolveRole returns "employee" for everyone and the CEO menu/alerts are unreachable until it is set.
  • The LLM path in the blocker flow is not covered by an automated test — attachNoteAndProcess calls Groq, so it is exercised only by the pre-existing live test and by manual use. Cost and latency of that call are unmeasured here.
  • Hindi is handled by the model prompt, not proven in these tests. The parser was verified in Hindi in T8; the onboarding/profile text is English-only regardless of the chosen language.
  • Session state is in memory. Losing the process mid-registration means re-tapping; not load-tested, and not shared across processes.
  • Alerts queued before a recipient is linked can never deliver — they carry chat_id = null, retry, and are then abandoned (observed live: 3 seed alerts abandoned). Only alerts created after linking will arrive.
  • createInvite marks the invite row is_synthetic = true even for a real person. The employee row it produces is correctly false; the invite row's flag is a cosmetic mislabel worth fixing.
