Why it was done this way

Scoped doorbells, not a second realtime server

Before, every change rang every open stream: with 300 people at five writes a second that is 90,000 doorbells a minute, each followed by a refetch. The plan named the fix (D92's own note): let the database say whose rows changed and let the API decide per stream. Nothing new to run — no Centrifugo, no Supabase Realtime — and D92's rule holds: no row content leaves the database by this path; the scope stays on the server. Everything fails open, because a missed doorbell is a board that silently goes stale while an extra one only costs a refetch.

Two queries for a picture, because RLS is per row

The first version asked RLS for everyone the viewer may see; Postgres ran the policy function on every row, and an org change took 9 s to settle for 300 people. A plain query lists the candidates, and RLS then decides among those — 25 times faster, and still the one rule that guards every read (G179, D207).

A PIN the server checks

The plan's first idea — a key on the phone unlocked by the PIN — fails on a shared phone: anyone holding it can try PINs offline against the stored key. So the PIN never leaves the server's check, is hashed with a secret the database does not hold, and every token is opaque and short-lived with a positive check on each request (D210). The user's 4–6 digits fall short of NIST's 8 for this case; that is written down as a deviation with a recommendation (6).

"Not in the mirror" is measured

The Operations page compares days. A comparison against a day the mirror never read — or read with a hole — would be confidently wrong. Whether time was read is a fact Postgres has (the sync's completed windows), so the page asks it, exactly, with range types, and shows "—" and a reason instead of a number it cannot stand behind (D214).

One notice change, honest in every part

Each re-consent stops people's updates until they agree, so the plan bundles the operations work into one change. Each part appears only when the system is configured for it, like every line before it — and two promises it makes were made true in code first: sign-ins are not readable by the question box or shown in the activity feed (D216), and the app's Firebase wake-up carries no content, a rule TASK-063 inherits (D213).

How it works

A live update

a write (any of 19 tables)→statement trigger: transition table → scope keys→ NOTIFY {table, op, at, scope}→API: each stream's picture hears it?→SSE: {table, op, at}→board refetches

e:<person> — anyone who may see that person; s:<person> — only that person (their inbox, a blocker they resolve); p:<project>; org — who sees whom changed, so every picture reloads; * — read-all viewers only. A trigger that cannot compute its scope sends * + org; more than 100 keys collapse to *.

A phone

dashboard: enrol → QR→phone: /device/enrol → device secret→lead: set-up code→ /device/credentials + PIN → person secret→/device/sign-in → fna_ (15 min) + fnr_→/device/refresh rotates

The device secret and person secret travel in headers; the PIN is checked as scrypt(HMAC(pepper, PIN)). A refresh token used twice ends its family; the 60-second grace covers a phone that lost the answer. On a company phone a new sign-in ends the previous person's session, and the session ends at the shift handover.

A photo

upload→type by first bytes→virus scan→clean (no location)→ sha256 of cleaned bytes→Storage (private bucket)→media_object row

A figure on the Operations page

cut      = greatest(day start, least(day end, now, Televend cursor))     -- in Postgres, microseconds kept
read     = range_agg(tstzrange(window_from, window_to)) over vends runs with complete = true

a side that is not read → null, and the page says why (before the mirror · a gap · nothing read yet today)

Concepts and techniques used

  • Statement-level triggers with transition tables — one notification per statement, scope computed from the changed rows (one trigger per event, G181).
  • Leakproof predicates and RLS — a planner may apply a leakproof filter before a security policy, which is what makes the candidate shortcut fast without weakening the policy (G179).
  • Range types and multiranges (Postgres 14+; live is 17.11) — range_agg merges read windows; <@ asks containment exactly.
  • EXPLAIN as an allow-list — the plan names every relation a query reads, CTEs and subqueries resolved, without running it.
  • Opaque tokens with rotation and reuse detection (RFC 9700 §4.14); scrypt + pepper (OWASP).
  • Content addressing (sha256 of cleaned bytes) with per-uploader records; MP4 box neutralisation (rename to free, zero in place — offsets stay valid, G176).
  • Code splitting with React.lazy and an error boundary; a one-time reload after a deploy.
  • CSP script hashes computed over what the browser parses (G180).
  • Emphasis chart design — one accent series, one gray context series, both validated for contrast in both themes; a legend and end labels; a table twin; dashed for the partial hour.

What we have not verified

  • No phone has signed in. The sign-in API is tested end to end over HTTP, but the app that holds its secrets (Android Keystore, allowBackup=false, FLAG_SECURE, attestation later) is TASK-063.
  • The Firebase wake-up is untried on any phone, Doze and battery saver included (A-T58.6).
  • The numbers are the laptop's, with Postgres on the same machine; the VPS has 8 shared vCPU (A-T58.3). The load test measures the doorbell, not the boards' refetches that follow it.
  • Notice 3.0 is a developer's draft — not reviewed by FreshNow or a lawyer, English only; its cash and stock lines describe what the app is planned to record (A-T58.7); Televend's server region is unconfirmed and its data processing agreement is not filed (A-T58.5).
  • Erasure does not reach names inside the Televend mirror (who filled a machine, in tv_refill and raw JSON) — Televend users are not mapped to employees yet (A-T56.2).
  • The question box's allow-list sees tables, not the inside of functions. A function the app role may call that reads another table is not caught by EXPLAIN; the ones in use return booleans or ids — not checked exhaustively.
  • The two-part Telegram request has not been seen arriving in a real chat yet; the bot's own long replies are not covered by a bot test.
  • Shift handovers 07:30 and 15:00 and the media retention periods are assumptions (A-T58.4, A-T58.1); deletion is off.
  • Screen readers were not tried on the chart; it has a title, a description and a table twin.
  • An independent review of parts 2–5 — see the review section below for what ran and what it found.
