TASK-018 — End-to-End Verification & Low-Literacy Hardening

Phase 1 (demo D6) · 2026-09-04 · Partially satisfies T18 (demo readiness) · Satisfies SPEC-000 R23 (no update lost) and R25 (escalate to a human, never guess)

One-sentence summary: Ran the whole loop end-to-end against real Telegram accounts (19/19 checks, real messages delivered to both phones), then had an agent role-play a barely-literate warehouse worker for 30 messages — which exposed six real problems the unit tests could never have caught, all traced to one root cause and fixed.

What was done

  • scripts/e2e-demo.ts — a 19-check end-to-end run against the real database, the real Groq parser, and the real running worker, using the two live Telegram accounts.
  • scripts/employee-sim.ts — drives one employee message through the real pipeline and prints what the system understood. Alerts it generates are suppressed so tests cannot spam the CEO.
  • Hardened packages/core/src/parse.ts: rewritten extraction prompt, new safety category, maxTokens 400 → 1200.
  • packages/core/src/updates.ts: needs_review now alerts a human.
  • packages/core/src/llm/client.ts: aggregate every provider's error instead of only the last.
  • Malayalam added to the consent notice and the bot's language picker.

Why it was done

Eighty passing unit tests said the system worked. They were testing the mechanism with clean inputs. The people who will actually use this bot are warehouse and delivery staff who may barely read or write, typing phonetically on a cheap phone in three languages. Nothing in the suite resembled that, so an agent was given that persona and told to try to use the system honestly.

How it works — what the stress test found

What was already right: across 30 runs, raw_text_preserved was true 30/30 and nothing crashed — the write-raw-first ordering held. And chatter, gibberish, "done boss" and 👍 produced zero false blockers, so the CEO was never spammed.

What was broken: six real problems produced no blocker at all.

The root cause was not what it looked like

Three of these looked like "the model cannot read Hindi/Malayalam". The stored error said AbortError: This operation was aborted — a timeout. Both were wrong. The client only reported the last provider's error, hiding the primary's. Once every provider's error was collected, the real failure appeared:

groq(openai/gpt-oss-120b) attempt 1 — HTTP 400: json_validate_failed, failed_generation: ""
groq(openai/gpt-oss-120b) attempt 2 — HTTP 400: json_validate_failed, failed_generation: "ma…"
nvidia(nemotron-…-reasoning) attempt 1 — HTTP 503: ResourceExhausted (946/16)
nvidia(nemotron-…-reasoning) attempt 2 — AbortError: This operation was aborted

gpt-oss-120b is a reasoning model. With max_tokens: 400 and JSON mode it spent its budget reasoning and was truncated mid-JSON, so Groq rejected the entire generation. The "ma…" fragment shows the second half of the problem: it had started replying in Malayalam prose, mirroring the employee's language, which JSON mode cannot accept.

So: a token cap and an unpinned output language, presenting as a language-comprehension failure and misreported as a timeout. Raising the cap to 1200 turned a case that failed 3/3 into one that passed 3/3.

The most dangerous finding

needs_review was a silent delete. The message was stored, no blocker was raised, and nobody was told — for exactly the employees least able to notice and rephrase. It now enqueues the raw words to the CEO for triage and writes an audit row, while the bot tells the employee it was saved but not understood.

Concepts and techniques used

  • Persona-driven adversarial testing — the failures were in the gap between "correct mechanism" and "usable by the actual person", which only a realistic user model reaches.
  • Error aggregation across a fallback chain — a fallback that masks the primary's error makes the primary undiagnosable.
  • Reasoning-model token budgeting — with constrained JSON output, tokens must cover the reasoning, not just the answer.
  • Pinning output language independently of input language.
  • Severity anchored to consequence, with realised harm never rated below the risk of the same harm.
  • Escalate-to-human on ambiguity rather than failing closed (SPEC-000 R25).

Research findings

  • Groq's json_object response format validates server-side and returns HTTP 400 json_validate_failed with a failed_generation field — which is what made the diagnosis possible once the error was surfaced.
  • The NVIDIA NIM fallback returns 503 ResourceExhausted on every call and then burns the full 10 s timeout. It provides no resilience today.
  • Bot token verified live as @freshnow1bot; both accounts had already run /start, so the bot was permitted to message them.

What we have not verified

  • Nobody has tapped through the bot on a real phone. Every flow was driven through the same core functions the handlers call, and Telegram delivery was proven — but button rendering, force-reply behaviour and message ordering in the actual app are still untested.
  • The fixes are prompt-level, not guaranteed. Each corrected case was re-run (some 3×) and passed, but an LLM is not deterministic. There is no automated regression test pinning these behaviours; a future prompt or model change could silently undo them.
  • The NVIDIA fallback is unusable and has not been replaced, so the system is effectively single-provider. A Groq outage means no parsing (updates would queue as needs_review).
  • The Hindi and Malayalam consent notices were written by me, not a native speaker. PDPL requires the person to understand what they consent to — both need review before real employees see them.
  • Cost and latency of the larger token cap are unmeasured beyond the individual llm_call rows; no sustained-load figure exists.
  • Only ~40 distinct messages were tested, by one persona, judged by the same agent that wrote them. Not a benchmark.
  • Voice (T16/T17) is still not built, and a genuinely non-literate employee would likely prefer speaking to typing — the accessibility gap this test exposed is only partly closed by text fixes.

Open questions

  • Replace or drop the NVIDIA fallback? As configured it costs ~20 s per Groq failure and never succeeds.
  • Should needs_review also auto-ask the employee to re-send, rather than only telling them it wasn't understood?
  • Should severity/category decisions be pinned by a golden-set regression test run on every prompt change?
  • Company Block A remains open: the real blocker taxonomy, real SLA windows, and the real resolver map are all still synthetic.
