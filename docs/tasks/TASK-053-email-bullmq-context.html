Why not Jev, and why not replace the portal with a PM tool

  • Jev would be another company receiving employees' words. Zero retention is a sales contract, not a setting. It is English-first while the workforce writes Hindi and Malayalam. And what it is built for — choosing a route, classifying — are the decisions CLAUDE.md keeps in rules. The model already used (through the one wrapper) extracts status and blockers; nothing here is limited by that.
  • Plane, OpenProject, Taiga, Vikunja, Huly are planners' desk tools. None captures a daily status from Telegram, routes a blocker by (category, site, shift) or escalates on an SLA, and each is more containers on a box Postgres already shares. What they get right was taken instead: short task keys (FN-42), reply-by-email updates (Jira), and confirm before assign.

The same architectural rules apply as for Telegram. The worker is a thin adapter and every decision is in packages/core. The employee's words are written before the model is called. Who and whether are decided by rules (owner check, role, the TASK-052 name rule). Every outbound message goes through the outbox. Each step is audited under one correlation_id.

Concepts and techniques

  • Message-ID threading: the ID we set is the anchor every reply quotes back. Deriving it from the outbox id keeps it the same across retries.
  • Authentication-Results (RFC 8601): the receiving server's verdict on SPF, DKIM and DMARC. Only the first header from the trusted server counts, because anything below it was written by the sender.
  • Plus addressing: one mailbox, a second address. The IMAP search reads only that address, so the rest of the mailbox is never opened.
  • Job schedulers: a schedule stored by id in Redis, upserted at every start. Concurrency 1 means a slow poll is never overlapped.
  • Lock-order deadlock: a foreign-key check takes a share lock on the parent row. If your own transaction holds that row FOR UPDATE on another connection, the check waits on itself.
  • Schema pruning with join closure: pick tables by signal words, then add the tables they join through, so a correct query can still be written.

How the earlier test sent Telegram messages "from the CEO to Hemanth"

Nobody's Telegram account was used. scripts/e2e-demo.ts (pnpm e2e) runs against the live database. It calls the same core functions the dashboard calls — assignTask, for example — with the CEO's employee id as the actor. Those write rows to notification_outbox. The running worker then delivers them through the Telegram Bot API with BOT_TOKEN. So every message comes from the bot, @freshnow1bot, into the chat each person opened with it. The chat ids exist because each of them pressed /start; the script reads them from CEO_TELEGRAM_USER_ID and E2E_EMPLOYEE_TELEGRAM_ID in .env. Claude Code could do this because it ran on a machine whose .env held the bot token and those ids. Unit tests use a fake token and a stubbed network, and send nothing.

What we have not verified

  • Gmail itself. This build machine cannot reach smtp.gmail.com or imap.gmail.com. The App Password login, plus-alias delivery, SEARCH TO on the alias, the \Sent label on self-sent mail, Gmail keeping our Message-ID, and the exact Authentication-Results header are all assumptions (A-T53.1–4). The first real run is pnpm email:check on the laptop.
  • Spam placement of FreshNow's emails in the recipient's Gmail.
  • Gmail's vacation reply being screened as automatic (A-T53.5).
  • Quote stripping in other languages: only English "On … wrote:" forms are recognised. A Hindi or Malayalam mail client may leave quoted history in the update. The words are kept either way.
  • Bounces are not handled. They return to the account's own inbox, not the alias.
  • A live model reading a CEO email into tasks was not run here (no route to Groq). The proposal path was tested with a stubbed model and the grounding rules; the nine model-dependent tests still need a working key.
  • The Docker/Supabase start on the laptop with migrations 0020/0021 was not run here; they were applied to the local test Postgres.
  • Real phones opening the Email tab — tested in Chromium at desktop and phone widths only.
  • PDPL fit of personal Gmail: [believed] Google's data processing terms cover Workspace, not personal Gmail. Fine for a two-person demo with test data; not for employees' real data.
