TASK-020 — Document Intelligence, Conversation Guards & Dashboard Navigation

Phase 2 (demo fast-follow) · 2026-09-08 · Extends T13 (assignment) and T12 (dashboard) · Satisfies CLAUDE.md rule 2 (the model proposes, a human commits), rule 3 (deterministic guards, auditable) and rule 4 (bounded)

One-sentence summary: A PDF full of jobs is now read and split into one tracked assignment per job routed to the person each names — instead of the whole file being forwarded to one person — plus two deterministic guards for the incident where an overnight question swallowed the next morning's instruction, a direct /log command, and a rebuilt dashboard navigation.

What triggered this

Four screenshots from a live session, each showing a distinct problem.

A · An overnight question ate the next morning's message

At 15:11 the CEO sent /invite; the bot asked for a name and never got one. The step was still live the next morning, so the 09:43 caption was accepted as the answer. The database ended up holding this:

codedisplay_name
3BYGXR4XAssign the tasks to hemanth based on the attached pdf document.

The assignment the CEO wanted never happened, and an invite code existed for a person named after a whole sentence. That code has been cancelled and the cancellation audit-logged.

B · The PDF was forwarded, not understood

One task was created — Assign tasks from PDF — with the raw file stapled to it. Nobody can report status against "here is a PDF". The document actually contained four numbered items of real work.

C · There was no way to just log a status

Daily capture was reachable only by tapping through a menu. There was no command for the one thing people are meant to do every day.

D · The document appeared to hang — and this one was not our fault

Both sendDocument calls were accepted by Telegram: outbox rows sent, 1 attempt, no retries. The recipient's client then could not pull the bytes. At that moment, from this machine, three independent symptoms:

  • setMyCommands failed on bot startup (the retry recovered it)
  • getFile returned Gateway Timeout for both stored file ids
  • the raw download threw ECONNRESET

Hours later the same file ids downloaded in 627ms and 187ms with valid %PDF- headers. Same code, same references — so the references were never bad and the transport was. This is now designed for rather than assumed away: downloadTelegramFile() retries three times with backoff, and on failure keeps the file held so retrying costs one message rather than a re-upload.

What was built

1 · Documents are read, split and routed

New packages/core/src/documents.ts. The document is downloaded, its text extracted, and the separate jobs inside it become separate assignments to the people it names. On the real document from the incident:

4 numbered items  →  6 tracked tasks, each its own assignment and its own message

1. Build the complete finalized DEMO platform for status logging and task assigning → Hemanth
2. Report back about previous tasks                                                 → Hemanth
3. Go to warehouse to get details of employees and production systems               → Hemanth
4. Check what is working in the warehouse and what can be due for maintenance        → Hemanth
5. Enter all data in the database and automate alerts in the dashboard               → Hemanth

Six rather than four because items 1 and 4 each contained two distinct jobs. Each has its own status thread, which "here is a PDF" never had.

The file is no longer forwarded by default. It goes only on an explicit tap (📄 Also send the file), and then rides on the first task only, so one document does not arrive six times.

2 · The plan is a proposal, not an autonomous write

planDocumentTasks writes nothing. The CEO sees every task and its owner and taps to create them. A task whose owner could not be resolved shows as "⚠️ nobody named — needs you to say who" and blocks the create button — the model never picks the nearest-looking colleague. Grounding is the same as everywhere else: the model returns an index into a list we supplied, validated on return.

Tested with a name that is real in the document and absent from the company ("Bartholomew Fitzgerald"): the task comes back with no assignee and needsOwner = true.

3 · Two deterministic conversation guards

packages/bot/src/guards.ts — rules, not model calls, because they guard a question the bot itself asked: they must behave identically every time, cost nothing, and be testable without a network. Both err towards asking: a false "not a name" costs one tap, a false "yes" mints a wrong record.

GuardRule
isStepStale30-minute TTL. Past it the step is dropped before the handler runs and the person is told — silent expiry would answer their next message in a context they no longer remember being in. A session with no timestamp counts as stale.
looksLikeName≤40 chars, ≤4 words, no sentence punctuation or digits, no instruction verb — and refused outright when a document is attached, because nobody staples a PDF to a name. On a "no" the bot asks which was meant.

4 · /log, /status, /mytasks

All three call one showLogBoard(), so the command cannot drift from the menu button. /log sits directly after /start in the Telegram command menu — reporting your day is the daily action, and menu-diving to reach it is a barrier for exactly whoever most needs it.

5 · Dashboard navigation

Eight pills in one horizontally-scrolling strip hid half the tabs off the right edge of a phone — the device this is actually read on, which makes that the same as not having them.

  • Grouped sidebar on a wide screen (Today / Work / Records / Tools); a 4-across grid on a phone with nothing scrolled out of reach.
  • A live count on each tab, so you can see where the work is without opening it; blockers and carry-over turn red when non-zero.
  • A breadcrumb naming what you are looking at and why.
  • The tab is kept in the URL hash, so a refresh, a bookmark or a shared link lands back on the same view.

Research

PDF text extraction in Node, checked at task start rather than assumed:

LibraryVerdict
unpdf 1.8.1Chosen. MIT, zero runtime dependencies, Node ≥22, published 2026-08-13. Ships a serverless build of Mozilla's PDF.js with canvas mocked. Zero deps matters on a box where every process competes with Postgres for CPU. The @napi-rs/canvas peer is for rendering only and is not installed.
pdfjs-distFull engine — layout coordinates, fonts, rasterization. More than text extraction needs.
pdf-parseSimple, but older and thinner than unpdf on the same underlying engine.

Measured on the real document: 1 page, 481 chars, 259ms.

Verification

  • 123 tests pass, typecheck clean (27 files, 1 skipped). New: 5 document tests, 4 document-assignment tests, 9 guard tests, 5 bot-flow tests.
  • The bot's own router is tested, not just core: flows.test.ts drives handleText with a stub context and asserts the incident message produces a question and no invite code, that a plausible name with a document attached is still questioned, that a real name still works, and that an expired step is announced.
  • Per-job assignment verified against the database — one assignment row and one outbox delivery per job; a mixed document gives each person their own task and only their own.
  • Non-forwarding verified — 0 attachment rows and 0 attachment outbox rows on a plain assignment; still 1 when the CEO opts in.
  • Dashboard verified live — script parses, all 15 referenced element ids exist, 71 divs balanced, 8 tabs and 4 nav groups present.
  • /log confirmed registered via getMyCommands.
  • Document planning ran against the real PDF from the incident, and the regression tests use its actual text.

What we have not verified

  • Nobody has run the document flow from a real phone. The handler wiring is covered by typecheck and a stub-context test, but no one has sent a PDF through Telegram and tapped "Create these tasks". This is the single most important thing to try next.
  • Only one real document has been tested — one page, English, a clean numbered list under a single governing heading. Multi-page documents, tables, Hindi or Malayalam text, and documents mixing several people under sub-headings are all untested. Where the boundary falls between "two jobs" and "one job in two clauses" is a model judgement and has not been measured across a corpus.
  • Scanned/image PDFs are handled but not tested with a real scan. The code path says "I could not find any text — tell me the tasks here"; that message has not been seen in practice. There is no OCR.
  • The 30-minute TTL is a judgement, not a measured figure — long enough to survive an interruption, far short of the overnight gap that caused the incident. It has not been validated against how people actually use the bot.
  • looksLikeName is English-centric. The instruction-verb list is English; a Hindi or Malayalam instruction would pass the verb check, though the length, word-count and punctuation rules still apply.
  • The new dashboard navigation has not been opened in a phone browser — it is verified by parsing and by markup assertions only.
  • Carried over: voice accuracy unmeasured; llm_call.cost_usd reports 0; the NL-query box still runs as the service role rather than under the viewer's RLS context.
