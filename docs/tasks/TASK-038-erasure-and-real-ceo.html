TASK-038 — Erasure has a caller, and the system finds the real CEO

2026-09-18 · no migration · api work.ts (one route) · core org.ts (ceoEmployeeId) · dashboard People tab · semantic catalogue · 362 tests green (from 360)

One-sentence summary: The PDPL erasure function built in TASK-037 can now be invoked — by the CEO, from the People tab, through a route that refuses everyone and everything else — and the four places that still assumed the CEO is the seeded demo row now look the real one up, so nothing in the system files work under, tells, or parents to a person who may not exist on a real org chart.

1 · Why

TASK-037 left two things open by its own admission. eraseEmployee existed with tests and no caller, which means the only "this person left" tool was the reset script's hard delete — the exact thing that broke replay in TASK-036 and the opposite of what PDPL and CLAUDE.md require ("erasure = anonymise, not delete"). And a grep for DEMO_CEO_ID found the seeded CEO row still hardcoded where the system needs a CEO: the needs-review alert, the parent of every newly onboarded employee, and the issuer recorded on every invite. On day one those are all the same row. On a real org chart — where the CEO role has been handed to a real person through the People tab — they would have alerted, parented and attributed to a demo record.

2 · What was built

Calls eraseEmployee with the viewer's id and the request's correlation id. Under /dashboard/* so the shared-secret and JWT hooks cover it — a new prefix would be unauthenticated by default. Authorization is explicit in the handler because core writes run as the service role and Postgres will not refuse them. The CEO-row rule is what keeps ceoEmployeeId() always able to find someone.

Two steps because it is irreversible and there is no backup of the words. The reason is chosen by a human and recorded, never inferred.
ceoEmployeeId()

A restart that was not a restart

Stopping the three background pnpm start:* tasks ended the pnpm wrappers and left every tsx child alive: the new API died with EADDRINUSE on 3001, and for a minute there were two workers polling the same outbox. The relay uses for update skip locked so nothing was delivered twice, but two SLA sweeps racing is not a state to leave running. The stale trees were ended by pid and the ports confirmed free before starting again. Recorded because "I restarted the services" would have been false without checking the listener.

4 · What was deliberately not built

  • Managers acting as managers on Telegram. The bot's resolveRole is still config-CEO or employee, so a manager can report their own work in the bot but cannot assign or see their reports' blockers there — the dashboard does that. Making the bot role-aware touches the directory, the assign callback, the blocker queue and the menu, each needing a refusal test; it is a task of its own, not an addendum to this one. It fails closed today, which is the acceptable direction.
  • Moving the bot's CEO identity off config. TELEGRAM_CEO_USER_ID + the seeded row remain the anchor for who the bot treats as CEO (ensureCeoLinked). Handing the role over in the dashboard does not change who the bot believes is CEO. That is two sources of truth, listed below as an assumption, and left because the alternative — the bot's CEO being whatever the database says — makes the dashboard's role control also the bot's identity control.
  • A CEO-row erasure path. Handing the role over first is the rule, and the route says so.

What we have not verified

  • The erase button has not been clicked through to completion in a browser. The confirmation and Cancel were exercised; the final "Erase" was not, because the only people on the live database are the demo cast and the user's own row. The route's happy path is proven by the suite against a synthetic person.
  • Erasure does not touch attachment rows, project narratives, or issue descriptions. eraseEmployee redacts task_update notes and assignment notes. A person's words in a project_update.narrative, a project_issue.description, or a document caption survive erasure today. Not a regression — nothing erased them before either — but it is a gap a data-subject request would expose.
  • An erased person's Supabase Auth user still exists. auth_user_id is nulled so they can no longer reach any employee row, but the login itself is not deleted from auth.users; that needs the service-role Admin API and a decision about whether the email is personal data to be removed.
  • The bot's CEO and the database's CEO are assumed to be the same person (A-T38.1). Nothing checks it.
  • The "two workers" minute produced no visible duplicate, but I did not audit every outbox row for that window; the row-lock design is what I am relying on.
