TASK-033 — Live sync: the board stops guessing when to look again

2026-09-14 · Phase 6 of the task & project portal plan · migration 0013 · core changes.ts · GET /dashboard/events · dashboard live.ts · 3 tests · 9/9 browser checks · 310 tests green

One-sentence summary: Postgres now tells the API when something changed, the API fans that out to every open board over Server-Sent Events, and a change made in one place appears in another in about 780 ms instead of up to twenty seconds — while the event itself carries no row content at all, so the stream cannot become a way around row-level security.

1 · The one security decision

The notification payload carries the table name and the operation. Nothing else. No id, no employee, no project.

LISTEN is a connection-level mechanism with no row security of its own: whatever goes into a payload is visible to every listener, and the API holds one listening connection shared by every signed-in viewer. Any identifier in that payload would therefore be a channel straight past RLS — an employee could learn that a blocker had been raised about a colleague simply by watching the stream.

So the event says only "something in task changed". Every client then re-fetches through the ordinary RLS-scoped endpoints and Postgres decides what each person actually sees. The stream is a doorbell, never a delivery. Two tests assert the payload has exactly the keys at, op, table — one on the listener, one on what crosses the wire — so anyone who later adds an id "just for convenience" gets a red test.

The cost, stated plainly: every connected client re-fetches on every change to a watched table, including changes it cannot see. At FreshNow's size (tens of employees, a few changes a minute) that is cheaper than the polling it replaces. At hundreds of concurrent viewers it would not be, and the fix then is per-viewer filtering in the API — not a richer payload.

2 · What was built

WhereChange
migrations/0013_live_sync.sql notify_change() plus a trigger on each of 19 tables a dashboard actually renders. Statement-level, not row-level: one notification per statement however many rows it touched, so a bulk update of 200 tasks rings the bell once. Deliberately excluded: audit_log, run_trace, llm_call (the highest-volume writes in the system and nobody watches them live), invites and consent records, and the alerting policy tables.
core/changes.ts One listening connection, fanned out to many in-process subscribers. It gets its own single connection, never a pooled one — LISTEN occupies a connection for as long as it listens, and a pool of 5 with one permanently blocked is a pool of 4 whose failure looks like unrelated queries hanging.
api/routes/events.ts GET /dashboard/events. Under /dashboard/* so it inherits the existing auth hooks. Capped at 50 concurrent streams (503 with a message telling the client to keep polling), a 25-second comment heartbeat so a proxy never cuts an idle stream, X-Accel-Buffering: no, a retry: hint, and cleanup on both close and error.
dashboard/lib/live.ts Reads the stream, debounces 400 ms, and keeps the poll — at 120 s while live, back to 20 s the moment it is not.
dashboard/App.tsxThe status line reads live or polling, so the state of the stream is visible rather than assumed.

Why fetch and not EventSource

This was found by the browser check failing, and it is worth recording because the obvious tool is the wrong one: EventSource cannot send an Authorization header. Its only way to carry a token is the URL — where it would be written into every access log, proxy cache and browser history entry on the way. The dashboard authenticates with a Bearer token, so the stream is read with fetch and a streaming body reader instead, carrying exactly the same headers as every other call. The cost is that reconnection is ours rather than the browser's, which is the capped backoff (1 s → 30 s); the benefit is that a session token never appears in a URL.

What we have not verified

  • A Telegram-originated change was not separately observed arriving live. The trigger is on the table, so any writer fires it and the bot writes to the same tables — but the browser check drove both sides from the dashboard. What is proven is write → Postgres → stream → a different session; the bot is one such writer, untested as such here.
  • Reconnection after a genuine network drop is untested. The backoff is written and the poll takes over in the meantime, but no test kills the connection and watches it come back. The "polling" badge is the honest signal if it ever fails to.
  • The 50-stream cap has never been reached. It is a guess at a sensible bound for a box with 8 shared vCPUs, not a measured limit.
  • Behaviour behind Caddy in production is untested. The headers that matter (no-transform, X-Accel-Buffering, the heartbeat) are set, but this ran without a reverse proxy in front.
  • The project portal does not subscribe. Live updates refresh the task board's data; a project page reloads when you act on it or revisit it. Nothing about projects updates live yet.
  • Every client refetches everything on any change. Correct and cheap here, but it is the thing that would need to change first under load — see the cost note above.
