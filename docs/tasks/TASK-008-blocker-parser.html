TASK-008 — Blocker Parser (core)

Phase 1 (demo) · 2026-09-04 · Satisfies SPEC-000 R19 (model translates, never computes/decides) and R23 (raw text persisted before any model call) · Turns a free-text update into a structured, routable blocker. 37/37 tests green; English + Hindi verified live.

What was done

  • packages/core/src/parse.ts — extractBlocker(text) (LLM → Zod-validated {is_blocker, category, severity, affected_asset?, risk?, summary}) and parseTaskUpdate(id) (read note_raw → extract → write note_parsed → create a blocker row, or flag needs_review on failure).
  • Fixed a jsonb double-encoding bug in parse.ts, audit.ts, and outbox.ts: ${JSON.stringify(obj)}::jsonb stored a jsonb string; switched to ${sql.json(obj)} which stores a proper object. This would have corrupted the outbox payload the real Telegram sender reads.
  • Tests — 3 pipeline tests (stubbed LLM, real DB): blocker created, needs_review on failure, non-blocker; plus a gated live test that ran real English + Hinglish through Groq.

Why it was done

The model translates; deterministic code decides. The parser extracts what kind of problem it is. It does not decide who resolves it or whether to escalate — that is Task 009 (a table lookup + a rule). This split is what keeps routing auditable.

Raw text is written before the model is called. The bot (Task 007) writes note_raw first; parseTaskUpdate runs afterwards. If the LLM is down or returns garbage, the update is not lost — it is flagged needs_review and can be re-parsed later. is_synthetic is inherited from the update, so a demo blocker is never mistaken for real.

How it works

parseTaskUpdate(taskUpdateId, correlationId)
  read note_raw, employee_id
  extractBlocker(note_raw)  ──▶ llmComplete(schema)   ← translate to validated JSON
     success → write note_parsed
        is_blocker? → insert blocker (raised_by=employee, category, severity, …)
        else        → no blocker
     failure → note_parsed = {needs_review:true, error}; NO blocker (raw kept)

Live check (2026-09-04, RUN_LLM_LIVE=1): English "chiller in van 2 not holding temp, juice at risk" and Hinglish "van 2 ka chiller theek nahi hai, juice kharab ho jayega" both classified as blockers with valid category/severity enums, ~2.7 s for the pair.

Concepts and techniques used

  • LLM-as-translator — free text → a fixed schema; the engine (Task 009) makes every consequential decision.
  • Write-raw-first — durability before derivation; a model outage never loses an update.
  • Graceful degradation — a parse failure becomes needs_review, not a crash or a fabricated blocker.
  • Correct jsonb binding — sql.json() (single-encode) vs the double-encoding trap of JSON.stringify + ::jsonb.

Research findings

Reused the Task 004 provider verification. New this task: a live multilingual check — Groq gpt-oss-120b handled English and romanized Hindi correctly on the two examples tried. This is a spot check, not a benchmark.

What we have not verified

  • The daily-logging Telegram UI is not built — parseTaskUpdate is the core the bot will call once a BOT_TOKEN exists (Task 006/007). The write-raw-first ordering is enforced there, not yet exercised end-to-end.
  • Extraction accuracy is measured on two examples only. No dataset, no accuracy/precision numbers, no Devanagari-script test, no noisy/ambiguous inputs. Severity calibration against real resolution times is future work.
  • No prompt-injection hardening on the free-text input.
  • The hourly reparse_failed retry job is not scheduled yet.
