TASK-030 — Task Depth: Steps, Progress as Evidence, Relations, Resolution

2026-09-14 · Phase 3 of the task & project portal plan · migration 0010 · core progress.ts · 7 routes · a task detail panel · 8 core tests + 6 route tests · browser-verified · 257 tests green

One-sentence summary: A task now carries its checklist, a percentage that always says what it is made of (counted, implied by status, or self-reported with a note), a start and due date with a "behind" flag computed in SQL, links to other tasks with the inverse written automatically, and a reason for stopping — and none of those numbers ever comes from a model.

1 · The design, and where it comes from

DecisionReference
Status → category (todo / in_progress / done) in a lookup table; reports run on the categoryJira status categories
Status ≠ resolution: resolution (done, won't do, duplicate, cancelled) set with the closing status, never aloneAtlassian's resolution-field guidance
Three progress sources, always named: counted from steps wins; status (pct_when_here) when there are no steps; self-reported only with a note, labelled, replaced by the next countOpenProject's published modes (work-based, status-based); the "90% complete syndrome" literature
One recursive task table (parent_task_id, task_type), not a table per levelOpenProject work packages, Vikunja, Focalboard
Relations separate from hierarchy; inverse row written in the same transaction; cap of 30; cycle check on ordering linksVikunja relation kinds; Asana's 30-dependency cap
"Behind" = elapsed fraction minus reported progress > 30 points, computed on read, shown as a flag, never a forecastYour choice; threshold [assumed]

What we have not verified

  • The status percentages are placeholders (open 0, pending 10, in progress 50, done 100). Editable in task_status; the company has not said what a "pending" task is worth.
  • The behind threshold of 30 points is assumed. One constant in tasks.ts, used by both the board and the panel.
  • Weighted rollup by estimate_minutes is stored but not yet used; counting treats every step as equal.
  • Subtasks have a parent link and appear in the panel; there is no UI to create one yet — steps cover the checklist case.
  • The bot does not show progress. Steps, percentages and relations are dashboard-only this phase; the bot's board is unchanged.

Security and honesty

  • A self-reported number can never be mistaken for a measurement: the source is a column, the note is mandatory, the UI colours it differently, and the history keeps every value.
  • Cascading deletes were introduced for the three child tables only, deliberately and documented in the migration; business rows still never cascade.
  • Every write route checks ownership or canAssignTo before calling core, with tests for the refusals.
