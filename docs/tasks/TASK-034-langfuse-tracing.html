1 · Why, given llm_call already exists

The llm_call table records every call's provider, model, tokens, cost, latency and success, and the daily budget cap reads it. It answers "what did this cost" perfectly well. What it does not answer is "what happened, in order" — that a parse was attempted on Groq, hit a 429, waited, fell through to OpenRouter, and the second answer failed schema validation, all inside one employee's message.

That is the question a trace viewer answers, and it is the one worth asking when something is slow or wrong. So: llm_call stays the record of cost — it must not depend on a third party, because the budget cap depends on it — and Langfuse is the timeline on top of it. Same facts, arranged for a different question.

2 · The three decisions

DecisionWhy
No SDK. One fetch against Langfuse's public ingestion endpoint, with basic auth. CLAUDE.md: no dependencies without a stated reason, on a box where every process competes with Postgres for 8 shared vCPUs. The SDK and its transitive tree would wrap one HTTP POST. The whole client is about 200 lines including comments.
Content capture is OFF by default. Metadata always; prompt and completion text only with LANGFUSE_CAPTURE_CONTENT=1. Prompts here contain employees' own words about their shift, in Hindi, Malayalam or English. Sending that to an observability tool is a data-protection decision, not a technical one. With a hosted Langfuse it means employee free text leaves the company, needing the same lawful basis, notice and consent as any other processing. The default is the one that cannot create that problem.
It can never break a model call. Fire-and-forget, a 5 s send timeout, a 200-event cap, every failure swallowed and counted. Losing a trace is acceptable. Losing an employee's update because an observability tool was down is not. The counters on /health are how a silently broken tracer becomes visible — because "fire-and-forget" and "quietly failing for a week" look identical without them.

The correlation id is the trace id

Every model call made during one run lands under one trace, because the existing correlation_id — already threaded from a Telegram message or an HTTP request through every write and every audit row — is used directly as the Langfuse trace id. A retry on a fallback provider is a second generation inside the same trace, with its own observation id keyed by (run, provider, model, attempt), so nothing overwrites anything.

Operations, named

All seven call sites now pass an operation, so the trace list reads as work rather than as a list of model calls: parse_update, classify_intent, resolve_context, plan_document, eod_summary, question_to_sql, narrate_answer. It affects nothing but the trace name.

4 · How it was switched on (and how to move it)

Currently pointed at Langfuse Cloud (EU), https://cloud.langfuse.com, with the keys in .env and nowhere else. The plan is to move it to a self-hosted instance on the VPS once that is finalised; changing LANGFUSE_BASE_URL and the key pair is the entire migration.

To point it somewhere else:

  1. Open the Langfuse UI and create (or pick) a project.
  2. Settings → API Keys → Create new API key. Copy the public key (pk-lf-…) and the secret key (sk-lf-…) — the secret is shown once.
  3. Put both in .env as LANGFUSE_PUBLIC_KEY and LANGFUSE_SECRET_KEY. Set LANGFUSE_BASE_URL if it is not the local instance.
  4. Restart the API, bot and worker. curl localhost:3001/health should show tracing.enabled: true.
  5. Send one message through the bot and look at the trace list.

Leave LANGFUSE_CAPTURE_CONTENT unset unless the consent notice has been updated to cover it.

What we have not verified

  • Only one operation has been traced for real — parse_update. The other six (classify_intent, resolve_context, plan_document, eod_summary, question_to_sql, narrate_answer) go through the same logLlmCall path, so they are believed to work, but none has been observed in the Langfuse UI.
  • The retry and fallback path has not been traced for real. The test proves two attempts get distinct observation ids under one trace; no actual provider failure has been watched arriving as two generations.
  • Traces now leave the machine. Langfuse Cloud (EU) receives metadata for every model call — model, provider, tokens, cost, latency, success. No employee text, because content capture is off. That is a deliberate choice made with the user; moving to a self-hosted instance on the VPS is the stated plan.
  • No load testing. The 200-event cap and 2-second flush are reasonable-looking numbers, not measured ones.
  • Only LLM calls are traced. Not the routing decisions, not the SQL the query agent runs, not the outbox. Those are already in audit_log and run_trace; unifying them into one trace view would be a separate piece of work.
  • Nothing flushes on shutdown. stopTracing() exists and nothing calls it, so a process killed within 2 seconds of a model call loses those traces. Acceptable for observability; stated rather than implied.

Security and privacy

  • No userId on any trace. Tying traces to an employee would create a per-person record of what they wrote and how the model handled it — precisely the individual profiling CLAUDE.md forbids. Traces carry a correlation id and nothing that identifies a person.
  • The keys live only in .env, like every other credential, and appear in no report, no knowledge-base entry and no memory file.
  • Content capture is a deliberate, separate switch with the PDPL consequence written next to it in .env.example, so nobody can turn it on without reading what it means.
  • The budget cap does not depend on Langfuse. It reads llm_call. An observability outage can never affect spend control.
