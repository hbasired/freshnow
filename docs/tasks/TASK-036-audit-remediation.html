TASK-036 — Audit remediation: security, traceability, and the things that failed silently

2026-09-18 · migrations 0014 + 0015 · core trace.ts (new) · replay.ts rewritten · 21 audit findings + 11 review findings closed · 338 tests green · every service restarted and verified live

One-sentence summary: An adversarial audit and a code review found a question box running as a role that could read password hashes, an RLS policy that let an employee promote themselves to CEO, a replay that reported 90% of real runs as diverged and a nonexistent run as clean, a trace table nothing but the seeder wrote, and a routing failure that lost a blocker forever — all are closed, each with a test or a live probe proving it, and every claim in the knowledge base that turned out false is corrected.

1 · Method

A subagent was given the four architectural rules, the knowledge base and a running system, and told to find what was broken rather than confirm what worked — running ~40 live queries, a privilege probe as the real freshnow_app role, and a diff of the semantic layer against information_schema. Separately, /code-review at high effort covered the dashboard rework. Every critical finding was re-verified independently before anything was changed, and each fix carries a test or a live probe. Three of my own probes were wrong before they were right; those are recorded too (§5).

3 · Traceability — CLAUDE.md rule 3, made true

Replay did not replay

It re-read the live blocker row to get the category, then re-derived. Two consequences: it was not a replay (a routing-rule change and a data change were indistinguishable), and because the reset script hard-deletes blockers while the audit log keeps pointing at them, 45 of 50 routed blockers no longer existed and every one reported diverged: true. Worse: a correlation id that never existed returned {steps: 0, checks: [], diverged: false} — "replayed fine".

Fix: blocker.routed now records its inputs (category, severity, site, shift) in the audit detail; replay re-derives from those and never touches the live row. A run that does not exist returns found: false. A run recorded before inputs were kept is counted unreplayable — unknown, not diverged. Six tests, including the three behaviours that were silently wrong.

5 · Where I was wrong before I was right

  • The first privilege trigger did not work. It was SECURITY DEFINER and tested current_user, which a SECURITY DEFINER function rewrites to the owner (postgres) — so the service-role escape hatch matched every caller. Fixed with session_user (G92).
  • My first probe of that trigger lied. It picked the target employee with a subquery that ran before the RLS context was set, saw no rows, and the UPDATE matched nothing — which raised nothing, which I counted as "allowed". A privilege probe must assert row_count (G93).
  • I added a uniqueness constraint on run_trace(correlation_id, step) that was wrong. One run can legitimately perform a step for several entities; the seeder routes three blockers under one id. The seed test caught it. Traces are append-only now, like the audit log.
