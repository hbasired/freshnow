Why it was done this way

Capabilities, not role names — one table, two copies, one test

Fourteen checks said "refuse if the role is employee". Adding a role value would have waved a VMO straight through them — to the people list, to starting projects, to turning a technician's email about a broken machine into a work proposal. A capability table inverts that: a role has exactly what it lists. The database needs the same answers for row-level security, so the table lives in permissions.ts and, seeded from it, in role_capability; a test asks Postgres every role × capability and compares.

Admin is not the CEO

app_is_ceo() is unchanged and still means the CEO alone; a new app_reads_all() is what the read policies ask. So Admin reads everything (the user's "full access"), while the CEO-only write policies, the guard on privileged employee columns (0014) and everything done in the CEO's name stay the CEO's (SPEC-000 R30). In code, Admin lacks one capability — making Admins — and core refuses any change to the CEO's own row by anyone but the CEO.

Only a role that leads people may be someone's manager

Escalation sends a raiser's own words to their manager. The "Reports to" picker offered anyone who was not an employee — so it would have offered a VMO, who must not read a colleague's words. Now core refuses it and the picker does not offer it.

Rules in core, not in each channel

Three of the four defects were rules enforced in the dashboard's route but not underneath it, so the bot — a second channel to the same core — skipped them. Task ownership, the CEO's withdrawal and every org change are now checked in core, where every channel passes.

What the review found — done by hand this time

The independent review (three reviewers and a skeptic, as for TASK-056) could not run: the review agents hit the account's weekly limit. Reviewing the change myself, adversarially, found two things, both fixed with tests:

  • An email address is an identity (D201). Inbound email decides who is speaking by the sender's address, and Admin may now set addresses — so an Admin could have pointed the CEO's record at a mailbox they control and given work by email in the CEO's name. Now the CEO's and an Admin's address are the CEO's to change.
  • A CEO ability removed by accident (D202). The first version refused any change to or from the CEO role, which also took away the CEO's existing way to hand the role over. Restored for the CEO alone.

The worker stopped for two hours — not this task's code, found during it (G174)

At about 19:28 Dubai the worker exited: the email client reported a dropped Gmail connection as an "error" event that nothing was listening for, and Node stops on that. Everything the worker does stopped with it — Telegram delivery, the SLA sweep, the Televend sync — until it was restarted at 21:40 (nothing was waiting to be delivered; the Televend mirror caught up in one run). The email client and the four BullMQ queues and workers now have error listeners; a test with a fake mail server that hangs up reproduces the exact error and shows it no longer escapes.

Concepts and techniques used

  • Capability-based access control, deny by default — a role holds a list of what it may do; anything not listed is refused.
  • Policy as code with a database twin — one table, two copies, a test that they agree.
  • Row-level security — reads are filtered by Postgres for every role, whatever the code forgets.
  • initPlan caching — (select fn()) lets Postgres evaluate a row-independent check once per statement.
  • Separation of identity and capability — "is the CEO" and "sees everything" are different questions with different answers.
  • Checks where every channel passes — rules in core, not in one channel's route.

Research findings

  • Supabase's RBAC guide uses the same shape: a role → permission table and a STABLE SECURITY DEFINER authorize() function the policies call, with the role carried in the sign-in token by an access-token hook. A third-party write-up (not the guide) notes such a claim stays stale until the token refreshes; here the role is read from the employee row for every transaction, so a role change takes effect at once.
  • Supabase's RLS performance guidance: wrap row-independent checks in (select …) so they become an initPlan; it reports large speed-ups on big tables (their measurements, not ours).

  • Whether a crafted identifier can slip set_config past the question box's guard and change the asker's RLS identity (role map, not verified). The question box is limited to roles that already see everything, so it could not widen anyone's view.

  • A Supervisor's "team" is their direct reports until teams exist (TASK-061) — an assumption, not FreshNow's org.
