TASK-012 — Role-based Dashboard

Phase 1–2 (demo) · 2026-09-04 · Satisfies SPEC-000 R9–R11 (a place to see everything; every number traceable) · A browser-viewable dashboard with RLS-enforced role scoping and the NL-query box. 3 RLS tests green; live HTTP health ok.

What was done

  • packages/api/src/routes/dashboard.ts — RLS-scoped JSON endpoints: /dashboard/employees, /dashboard/blockers, /dashboard/tasks (each read under the viewer's context via withContext), and POST /dashboard/query (the NL-query).
  • packages/api/src/dashboard-page.ts — a self-contained HTML page served at /: a "view as" role switcher, KPI cards, blocker/task/employee tables with SYNTH badges, and the natural-language query box that shows the answer, row count, gate verdict, and the executed SQL.
  • Tests — 3 inject() tests: serves the HTML; CEO sees all blockers while an employee sees only their own; an employee sees only their own employee row. Verified live over HTTP (health ok/ok).

Why it was done

The CEO needs one place to see everything; an employee must not see another's data. That boundary is enforced by Postgres RLS at the query, not by the handler: each read runs under withContext({employeeId | isCeo}) on the RLS-enforced app role, so a bug in a route cannot leak another employee's rows.

Deviation from the spec's Next.js dashboard (recorded in DEVIATIONS.md): for the demo it is served as a self-contained page from the existing Fastify API — same "see everything + ask in natural language" value with none of the Next.js/React/build weight. Production would use Next.js.

How it works

browser (view as CEO / employee)
   │  GET /dashboard/blockers?viewer=…
   ▼
withContext({isCeo|employeeId}) → app role → RLS filters rows in Postgres
   │
   ▼  tables + KPIs (synthetic rows badged)
POST /dashboard/query {question} → answerQuestion → answer + SQL + gate verdict

Run it: pnpm dev:api then open http://localhost:3001. Live check: server listened on :3001 and /health returned ok/ok; the RLS tests confirmed CEO=all, employee=own.

Concepts and techniques used

  • RLS at the read boundary — role scoping is a database guarantee, not application logic.
  • withContext — per-request transaction-local identity, pooling-safe.
  • Self-contained page — no build step, no CDN; opens straight from the API.
  • Evidence in the UI — the NL-query box always shows the SQL and the gate verdict.

Research findings

No new external research; reused SPEC-003 and the T14 query core. The design choice (Fastify-served page vs Next.js) is a demo-scope trade-off, recorded as a deviation.

What we have not verified

  • No real authentication — the "viewer" is a request parameter, so anyone could pass viewer=ceo. The RLS scoping is real, but who may claim to be the CEO is not enforced yet (a login/session is future work).
  • Browser JS rendering not verified in an actual browser — the endpoints are proven via inject() and live HTTP health, but the page's client-side fetch/render was not exercised in a real browser here.
  • The NL-query still runs as the service role (not per-viewer RLS-scoped) — see TASK-014.
  • No pagination, no charts/trends, no auth-gated write actions.
  • This is a deliberate deviation from the Next.js dashboard in the spec.

Open questions

  • Real auth (session/login) so "view as CEO" is a right, not a URL parameter.
  • Move to Next.js for production, or keep the served page for the pilot?
