TASK-003 — Core API Skeleton

Phase 1 (demo) · 2026-09-04 · Satisfies SPEC-000 R9/R11 (audit + traceability) · Fastify server with correlation-id propagation, a consistent error model, a DB-aware health check, an append-only audit helper, and the first real endpoint (CEO invite). 22/22 tests green.

What was done

  • packages/api/src/server.ts — buildServer(): an onRequest hook that mints or echoes an x-correlation-id; a single error handler (ZodError → 400, others → mapped status with a consistent {error:{code,message,correlationId}} shape); a 404 handler.
  • Routes — GET /health (checks Postgres with select 1) and POST /employees/invite (creates a single-use code + writes an audit row).
  • packages/core/src/audit.ts — logAudit() appends to audit_log via the service role.
  • packages/core/src/invite.ts — generateInviteCode() (unambiguous alphabet) and createInvite(); DEMO_CEO_ID added to meta.ts.
  • packages/api/src/server.test.ts — 5 integration tests via Fastify inject(): health, correlation-id echo, 404 model, invite creation + audit row, and 400 on bad input.

Why it was done

Channel-agnostic core (CLAUDE.md rule 1). The bot, dashboard, and later adapters must all call the same API, so domain actions (like issuing an invite) live behind HTTP + packages/core, not inside a bot handler.

Correlation id from the edge. SPEC-000 R9/R11 require every state change to be traceable. Minting/propagating one id per request — and echoing it — lets a single run be followed across the API, the worker, and audit_log.

Explicit Zod parse over the type provider. Research found the current fastify-type-provider-zod targets Zod 4.1's decode() APIs; the codebase is on Zod 3.x (to keep the T2 suite stable). Rather than take a risky Zod 4 upgrade mid-build, request bodies are validated with an explicit Schema.parse(req.body), which is exactly the "unknown + Zod parse at boundaries" rule and adds no coupling.

How it works

onRequest ─▶ req.correlationId = inbound x-correlation-id  ??  randomUUID()
             reply header x-correlation-id: <id>

POST /employees/invite
  Schema.parse(body)  ──(ZodError)──▶ 400 {error.code:"validation_error"}
     │ ok
     ▼
  createInvite()  ─▶ insert invite_code (service role)  ─▶ returns code + expiry
     ▼
  logAudit({correlationId, action:"invite.created", entityId:code})  ─▶ audit_log
     ▼
  201 {code, expiresAt}

The audit helper uses the service role (append-only for the app role, so the API path cannot rewrite history). The invite code uses an alphabet with no 0/O/1/I/L because people read codes off a screen.

Concepts and techniques used

  • Correlation-id propagation — one id per run, accepted-or-minted at the edge and echoed, so logs and audit rows join up.
  • Boundary validation — untrusted request bodies parsed once, at the handler edge, with Zod.
  • Consistent error envelope — every failure returns the same shape including the correlation id.
  • In-process integration testing — Fastify inject() exercises the real routes, error handler, and database without opening a socket.
  • Append-only audit via role separation — writes go through the service role; the app role has no UPDATE/DELETE on audit_log.

Research findings

  • fastify-type-provider-zod (2026) — actively maintained but uses Zod 4.1 decode() and z.output serialization. Rejected for now to avoid a Zod-major upgrade; revisit if/when the codebase moves to Zod 4.
  • Fastify 5.12.1 installed. Note: Fastify 5 types the error-handler argument as unknown — handled by narrowing (instanceof ZodError) then reading statusCode/message defensively.

What we have not verified

  • No authentication yet. POST /employees/invite is open — "only the CEO may invite" is enforced in Task 006/012 (bot CEO check / dashboard session), not here.
  • Invite-code collision (astronomically unlikely at 318) would throw on the UNIQUE constraint and surface as a 500; no retry-on-collision yet.
  • /health checks Postgres only — not Redis, and not the LLM providers.
  • The server has only been exercised via inject(); it has not been run as a live listening process, and not under load or with Redis down.
  • No rate limiting, CORS, or request-size limits configured yet.
