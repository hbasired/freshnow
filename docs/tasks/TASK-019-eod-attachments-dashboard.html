TASK-019 — EOD Reports, Attachments, Multi-Item Messages & the Operations Dashboard

Phase 1–2 (demo fast-follow) · 2026-09-07 · Extends T12 (dashboard) and T13 (assignment) · Satisfies CLAUDE.md rule 2 (the engine computes, the model narrates) and rule 4 (every loop is bounded)

One-sentence summary: Made the CEO's view actually answerable — alerts that name who is stuck and quote them, an end-of-day report per person computed in SQL, assignments that carry documents and can name several people at once, and a dashboard rebuilt around Completed / Pending / Blockers tables with carry-over by date — and in the process found three real defects that no existing test could have caught.

What was asked for

  • Ask the right person a question when something is missing, instead of guessing.
  • The CEO's blocker alert must say who and give the details.
  • An assignment must not parrot the CEO's sentence back at the employee.
  • Assignments may carry documents, and may contain several tasks.
  • A full end-of-day report per employee, stored in the database, readable by the CEO in the bot and on the dashboard.
  • A dashboard that actually populates completed / pending / blocker tables with notes, is clickable, shows who was assigned what that day, and surfaces anything carried over from earlier dates with names and reasons, segregated by date.

What was built

1 · CEO alerts that identify a person

The alert used to carry a category and a severity and nothing else — the CEO could see that something equipment-related was critical, but not who was stuck or what they said. routeAndAlert now joins the raiser and the originating update:

⚠️ CRITICAL · equipment — van 2 chiller

👤 VERIFY Rashid (delivery · Al Quoz warehouse)
📋 Task: Afternoon Marina route

💬 "boss van 2 ka chiller kaam nahi kar raha, juice kharab ho jayega"
⚠️ Risk: cold chain / spoilage

Their exact words are reproduced verbatim, in whatever language they wrote — the CEO reads what was actually said, not a translation of it.

2 · Titles are extracted, questions get asked

"Assign hemanth the task of demo presentation" used to create a task literally called "Assign hemanth the task of demo presentation". The context prompt now carries explicit title-extraction rules, and the result is Demo presentation.

When something is missing the system asks rather than guesses: no assignee named → the extracted title is held on the session (assign_pending) and the CEO is asked who; a report that matches none of an employee's tasks and they have more than one open → the words are held (which_task) and they are asked which. Nothing is filed loose and nothing is invented — with exactly one open task the answer is obvious and no question is asked.

3 · Several work items in one message

resolveMessage returns items[], each with its own task, title and assignee. Every index is still validated against the lists supplied to the model, so a multi-item message can no more invent a person than a single-item one could. Capped at MAX_ITEMS = 8 — an unbounded list from a model is an unbounded number of writes.

"tell Rashid to fix the van 2 chiller and ask Priya to restock the Marina machine"
  → Fix van 2 chiller            → Rashid
  → Restock the Marina machine   → Priya

4 · Documents and photos

New attachment table (migration 0004). We store Telegram's file_id and the metadata — never the bytes. Telegram accepts a file_id wherever an upload is expected, so sending the spec sheet on to the assignee is a reference pass: nothing is downloaded and no employee document sits on this machine. That is also the better PDPL position.

Telegram delivers a file and the message explaining it as two separate updates, so a caption-less file is held on the session until the next message says what it is for. Each file is queued as its own outbox row, so one failing attachment cannot block the instruction and a retry cannot double-send.

5 · End-of-day report per employee

New daily_report table (migration 0003), one row per person per day, regeneration replaces rather than duplicates. Every number is computed by Postgres over every row. The model receives the already-final counts and writes only the prose; if it is unavailable the report is still produced, just without the narrative. Readable by the CEO via /eod in the bot and on the dashboard; an employee sees only their own, enforced by RLS.

6 · The dashboard, rebuilt

Structure follows operations-dashboard practice: at most nine headline metrics, ordered so the ones that change what the CEO does today come first (urgent open, open blockers, carried over), each clickable straight through to the table that explains it; detail tables underneath; and a data-freshness line that is always visible — a stale number that looks live is the failure mode that matters.

TabAnswers
TodayCompleted / Pending / Blockers as three real tables — person, task, time; click a row for their exact words. Plus "could not be read — needs a human".
Carry-overEverything still open, grouped by the day it was raised, with an age column. "What is still hanging over from Tuesday" at a glance.
AssignmentsWho gave what to whom, with a file count, delivery state and the task's current status.
End of dayStored reports with counts and narrative; a button regenerates them.
People / Activity / Ask / How it worksDirectory, audit stream, guarded NL→SQL, and the flow diagrams.

Every table is filtered by a date picker and a viewer selector, and the viewer selector is not cosmetic — reads run under that person's RLS context, so the page shows exactly what they are allowed to see.

Three defects found while verifying

A · A whole class of tables was unreadable (G28)

Migration 0001 ran grant … on ALL TABLES IN SCHEMA public. That grants on the tables that exist at that moment — it is not a standing rule. Every table added since (bot_session, daily_report, attachment) had a correct RLS policy and no privilege behind it. The policy said yes; the grant said nothing.

It surfaced as a bare HTTP 500 on the CEO's end-of-day view. Every unit test passed, because tests run as the service role — which is BYPASSRLS and had its own grants.

Fixed by migration 0005, which re-grants and adds alter default privileges so later migrations are covered automatically, then re-revokes update, delete on audit_log — the blanket re-grant would otherwise hand back the ability to rewrite history. Guarded by db.grants.test.ts, which fails if any base table lacks SELECT for the app role.

B · The test database had stopped at migration 0001 (G29)

vitest.global-setup.ts applied only 0001_init.sql, so three migrations' worth of tables simply did not exist in the test database — and the "semantic layer stays in sync" test had been checking the yaml against a stale schema. The setup now applies every migration in order.

C · The first EOD report told the CEO the wrong numbers (G30)

It reported that Hemanth had five pending items. He had two — he had sent five messages about them. And it reported 0 blockers on a day a high-severity blocker was raised and escalated, because it counted the button tap (task_update.status = 'blocker') while the blocker had been detected by the parser inside a message tapped "pending".

Both numbers were computed in SQL exactly as the rules require — they were the wrong queries. Determinism buys nothing if the thing being computed is not the thing the CEO means. Completed and pending now count distinct work items; blockers are counted from the blocker table. Pinned by two tests.

Verification

  • 100 tests pass, typecheck clean (23 files; 1 skipped — the live multilingual parse contract test). New: 4 attachment tests, 5 EOD tests, 2 privilege tests.
  • CEO alert verified against the test database — all six assertions passed: names the person, says where they work, names the task, quotes their words verbatim (Hindi included), states severity, names the affected asset.
  • Title extraction verified live — "Assign hemanth the task of demo presentation" → Demo presentation, and with no matching colleague it returned no assignee rather than guessing.
  • Multi-item verified live — the two-person message produced exactly two assignments with the right titles and the right people.
  • All 8 dashboard endpoints return 200 and respect RLS: as CEO, 6 open tasks and 7 EOD reports; as Hemanth, 2 open tasks and 1 EOD report — his own.
  • The dashboard's embedded script parses (checked with new Function) and every element id it addresses exists in the markup.
  • Verification ran against the test database so no message reached a real phone.

What we have not verified

  • No real document or photo has been sent through Telegram to this build. The attachment path is covered by tests against the database and by the documented Bot API contract, but the round trip on a real phone — send a PDF, watch it arrive with the assignee — is untested.
  • A file_id is not a durable archive. It is scoped to this bot and Telegram makes no permanent-retention promise. If an attachment ever needs to be the record, production must mirror the bytes and set a retention policy. Treating a file_id as permanent storage would be a mistake.
  • Multi-item splitting is verified on one message, not a corpus. Where the boundary falls between "two jobs" and "one job described in two clauses" is a model judgement, and it has not been measured across the phrasings a real workforce uses — particularly in Hindi and Malayalam.
  • The EOD narrative is model-written. The counts cannot be wrong, but the prose can still emphasise the wrong thing. It has not been reviewed by anyone who runs the operation.
  • No scheduled EOD job yet. Reports are generated on demand — by /eod or the dashboard button. Nothing runs them automatically at end of shift.
  • The dashboard has been verified endpoint-by-endpoint and by parsing its script, not by a human clicking through it in a browser on a phone.
  • Voice accuracy remains unmeasured. No WER figure exists for Hindi or accented English on this setup.
  • llm_call.cost_usd still reports 0 — no pricing entry for the current model ids. Latency and counts are real; cost is not.
  • The NL-query box still runs as the service role, not under the viewer's RLS context (carried over from TASK-014). An employee must not be given that box until it does.
