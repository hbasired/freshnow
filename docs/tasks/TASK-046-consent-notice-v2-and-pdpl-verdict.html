One-sentence summary: The consent notice people had agreed to never mentioned Telegram's servers abroad or the AI services that read every update. There is now one notice for the bot and the app, built from the system's own configuration, so it names exactly what is used. Everyone is asked again in Telegram and in the app, and until a person agrees nothing is taken from them and nothing is sent to them abroad. Both CEO decks now open with a plain verdict: yes, the law applies; no, it does not force data to stay in the UAE; and here is what that means for us.

What was built

  • One notice, generated from the configuration (D139). consentNotice() builds the section "Where your data goes beyond FreshNow's database" from the same variables the senders and model client read:
    • Telegram, if there is a bot;
    • each AI provider with a key, in a fixed order, and voice transcription through Groq;
    • the push relays, if web push is set up;
    • email, chat and Langfuse, when content capture is configured;
    • the retention period.
    Version 2.0-draft, SHA-256 of the exact words.
  • Current consent only. A record counts only if it is for this version and today's hash. Adding a provider or setting RETENTION_DAYS therefore puts the notice to everyone again. Re-ordering providers does not.
  • Three doors (D140):
    • The bot answers anything from a linked person without current consent with the notice and "✅ I agree / Not now". It stores nothing, and says the message was not recorded.
    • The API returns 403 consent_required on every data route. /dashboard/me, the consent routes and the live stream stay open.
    • The outbox relay does not claim Telegram, push, email or chat rows for that person. They wait with no attempt spent and go out on the first poll after they agree. The inbox and the request itself are never held.
  • Everyone is asked (D141): the worker runs requestConsentFromEveryone() every minute. It sends:
    • Telegram: the notice with buttons whose data carries the first 16 hex characters of the hash, so a tap under older words records nothing;
    • the inbox;
    • web push, where a device is on.
    Each person is asked once per version of the words, and only on channels that are switched on.
  • Dashboard:
    • The gate says "The privacy notice has changed" and names the older version.
    • The consent card distinguishes current from out-of-date consent.
    • A consent_required answer mid-session brings the notice back instead of a board of errors.
  • Removed: the separate app notice (appConsentNotice, app-draft-1.0) and the machine-written Hindi and Malayalam text of 1.0. Everyone sees English until a native speaker writes the translations.
  • Decks:
    • a verdict slide 2 in both, and every slide number and cross-reference shifted by one;
    • the sector slide retitled;
    • consent claims updated ("must be re-issued" → "built 28 Sep");
    • the 28 Sep PDPL re-check, sources and not-verified items added.
  • Guides: DEMO-GUIDE.md, DEMO-GUIDE-APP.md, CHANNELS-GUIDE.md and docs/WHAT-WE-NEED-FROM-FRESHNOW.md describe the first-start "I agree" step and the troubleshooting.

Why it was done this way

  • Generated rather than hand-written recipients. The defect being fixed was a notice that under-named its recipients. A hand-kept list would drift again the first time someone adds a key. A notice built from configuration cannot name less than the system uses.
  • Controls at the doors, not a screen. TASK-045's gate was only in the UI, and a token could read the API directly. The bot, the API and the relay are the three places data enters or leaves, so each checks.
  • Hold instead of drop. Messages to someone who has not agreed are the company's record. Dropping them would lose work, while holding them costs nothing and delivers them on agreement (A-T46.3 asks the CEO whether held messages should expire).
  • No synthetic exemption. The existing consent.missing audit exempts demo rows, but the seeded DEMO CEO row is the real CEO's Telegram account, so an exemption would have skipped the one person who most needs to agree.

What we have not verified

  • A real Telegram tap. The live run deliberately used no bot token. The Telegram path was tested through grammY with the Bot API intercepted. The first real "✅ I agree" tap will happen on the laptop.
  • The legal reading. Whether employee consent is a valid transfer ground, and whether it may be a condition of using the tool (A-T46.1), is for counsel. The verdict slides say so.
  • The wording. Notice 2.0 is a developer's draft. FreshNow and a lawyer have not reviewed it. There is no Hindi or Malayalam version.
  • The regulator news rests on four reports read through search. No government page was readable from this session.
  • The database host is not named in the notice. The configuration does not know where Postgres runs. Naming the host once it is chosen is a one-line change, and it re-asks everyone.
  • Messages about a person sent to someone else (for example the CEO's Telegram quoting an employee's older words) are held by the recipient's consent, not the subject's. New words are covered because the doors refuse them; older records forwarded later are not re-checked.
  • Held messages never expire (A-T46.3).

Designed, not built

A "no transfers" mode for people who decline. If counsel says consent may not be a condition of using the tool, someone who declines should still be able to work. That means:

  • the app only;
  • their words never sent to a model (routed to "needs a human reader" in the inbox only);
  • nothing about them sent to Telegram.

The pieces exist: the relay hold, the needs-review path and the per-person channel preferences. What is missing is a recorded "declined transfers" state and a model call that checks it.
