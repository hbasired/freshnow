TASK-004 — LLM Wrapper (Groq primary, NVIDIA fallback)

Phase 1 (demo) · 2026-09-04 · Satisfies SPEC-000 R13 (llm_call logging), R15/R17 (bounded loops & retries), R19 (translate, don't compute), and the "single wrapper" rule · One entrypoint for every model call. 29/29 tests green.

What was done

  • packages/core/src/llm/client.ts — llmComplete({messages, schema, correlationId}): the single LLM entrypoint. Returns a Zod-validated object.
  • extract.ts — tolerant JSON extraction (handles code fences and prose-wrapped JSON from reasoning models).
  • cost.ts — best-effort token→USD estimate feeding the daily budget cap.
  • Model IDs corrected — a live query showed Groq no longer serves llama-3.3-70b-versatile. Primary is now openai/gpt-oss-120b (verified); fallback is the NVIDIA nemotron model. Updated in config.ts, .env, .env.example.
  • Tests — extract.test.ts (4) + client.test.ts (3, stubbed fetch + real DB): success+logging, provider fallback, and budget-exceeded degradation.

Why it was done

One wrapper, by rule. CLAUDE.md forbids calling a model from handlers. Everything goes through llmComplete, so schema validation, retries, timeouts, cost logging, and the budget cap are enforced in exactly one place.

The model translates; it never computes. llmComplete takes a Zod schema and returns a validated object — it turns free text into structure, and nothing it returns is a number it invented (SPEC-000 R19). Aggregation stays in Postgres (Task 014).

Bounded, always. A 10 s timeout, one retry per provider, then the fallback provider — then it gives up with LlmError. Over the daily budget it throws LlmBudgetExceededError so callers degrade to rules-only rather than spend without limit (SPEC-000 R15/R17).

How it works

llmComplete({messages, schema, correlationId})
  │
  ├─ dailySpendUsd() ≥ budget?  ──▶ throw LlmBudgetExceededError  (degrade to rules)
  │
  ├─ for provider in [groq, nvidia]:
  │     for attempt in [0,1]:              ← one retry
  │        fetch {base}/chat/completions   ← AbortController, 10 s
  │           response_format: json_object, temperature 0
  │        extractJson(content) ─▶ schema.parse(...)   ← validate
  │        logLlmCall(tokens, cost, latency, success)  ← llm_call row
  │        return validated object
  │     (on failure: log failure, try next attempt / provider)
  │
  └─ all failed ──▶ throw LlmError

Live check (2026-09-04): a single Groq call with openai/gpt-oss-120b on "chiller in van 2 not holding temp, juice at risk" returned {"status":"blocker","category":"equipment","severity":"high"} using 146 prompt + 186 completion tokens.

Concepts and techniques used

  • Single-wrapper boundary — one module owns every model call and its guardrails.
  • Structured output + tolerant parsing — request json_object, then extract-and-validate so a chatty or reasoning model can't corrupt state.
  • Bounded retries + provider fallback — a fixed attempt budget, never an unbounded loop.
  • Budget circuit-breaker → graceful degradation — spend is checked before every call; over cap, the system falls back to rules.
  • Cost/latency/token observability — every call writes an llm_call row.

What we have not verified

  • Committed tests stub the network — the wrapper logic is proven, but the only real API call was a single manual Groq check. The NVIDIA fallback has not been live-tested for json_object support.
  • Cost is a $0 placeholder (free tier). The budget cap mechanism is tested by inserting a synthetic high-cost row; real per-token pricing is UNVERIFIED.
  • Hindi/Hinglish extraction quality is unmeasured — contract tests across languages come with the parser task (Task 008).
  • Behaviour under provider rate-limiting / 429s, and under real latency, is untested.
  • No prompt-injection hardening on the free-text input yet.
