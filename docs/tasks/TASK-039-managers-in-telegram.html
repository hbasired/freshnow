TASK-039 — Managers act as managers in Telegram

2026-09-18 · no migration · core roles.ts, org.ts · bot bot.ts · first test of the bot through grammY's real handleUpdate · 375 tests green (from 362)

One-sentence summary: A person the CEO makes a manager or department lead on the dashboard's People tab now gets a manager's menu in Telegram — their team's blockers, assigning to their reports — decided by the same canAssignTo rule and the same RLS policy the dashboard uses, re-checked at every step because callback data is guessable; and a pre-existing gap where a crafted callback could turn a document into tasks for anyone was closed on the way.

1 · Why

Since TASK-030's org model the dashboard has known three levels — CEO, manager/lead, employee — but the bot's resolveRole knew two: the configured CEO Telegram id, and everyone else. A manager could report their own day in Telegram and nothing more; their team's problems and the assign button lived only in the browser. It failed closed, which was the acceptable direction, but it meant the channel most of the workforce actually uses did not know the org chart the CEO had drawn.

2 · Research

grammY's own deployment checklist and transformer guide (read 2026-09-18) describe the testing approach used here for the first time in this repo: feed sample Update objects to bot.handleUpdate and intercept every outgoing Bot API call with a transformer installed via bot.api.config.use, returning a fake ApiResponse so no HTTP call is made. grammY 1.46 is what is installed; nothing in the API surface used here has moved. No other research was needed: the permission rule already existed and was already tested.

3 · What was built

PieceWhat it doesWhy that way
botRole(isConfigCeo, accessRole)
core/roles.ts		 Pure. The configured Telegram id is CEO with or without a row; a row with access_role = 'ceo' is CEO too; manager and lead both give the manager menu; anything else is an employee. Role gains "manager". Two sources of identity, both honoured: config as the anchor, the row as what the People tab sets. The difference between manager and lead (department reach) is decided by canAssignTo, never by the menu string — the menu asks "may I show the button?", the rule asks "may this person do this to that person?", every time.
listAssignable(viewer)
core/org.ts		 The directory keyboard's people: CEO everyone but self; manager their reports; lead their reports plus their department (case-insensitive, trimmed, like the policy); employee nobody. The SQL twin of canAssignTo, so the bot never lists a name the write would then refuse. Self is excluded — "Add a task" is the self path, and a directory with your own name in it is how work lands on the wrong list.
listOpenBlockersFor(viewer)
core/org.ts		 The CEO's whole queue, or — for a manager — the query run under row-level security as that person (withContext, read-only). The reporter is left-joined so a blocker routed to the manager by someone whose row they may not read still shows, with the name withheld. The bot's /blockers and the dashboard's list are now literally the same policy (blocker_select) and cannot drift.
Bot auth middleware The one existing query now also reads access_role and department, builds ctx.viewer (the same shape the API builds for a signed-in user) and sets ctx.role through botRole. One query per update, as before. No new round-trip.
Manager menu and /help 🚨 My team's blockers · 📌 Assign a task to my team · 📋 Log daily tasks · ➕ Add a task · 👤 Update my details. No invite (CEO only, matching the API) and no document-to-tasks. A manager's day is their own work plus their team's problems.
/assign, directory, typed name, assignto: tap, the final write Open to CEO or manager. The directory is listAssignable; a typed name resolves only among those; the tap re-checks canAssignTo (alert, not silence, on refusal); the title step re-checks once more before assignTask ("no longer reports to you"). Callback data is an employee id anyone can type into a modified client. The directory having shown a name is not authorization; the rule at the write is.
Plain-text "tell Rashid X and Priya Y" Open to managers; each named person is checked; the ones outside the team are reported back by name ("Omar does not report to you, so I did not assign anything to them"), the rest assigned. The resolver sees every colleague as a candidate, so filtering has to happen after resolution. Silent drops are how someone believes a job was handed out when it never was.
Document planning — a pre-existing hole Only the button was CEO-gated; doc:read callback data and planFromDocument never checked the role, and docplan:go assigned to everyone the plan named. Now the planner refuses non-CEOs at the function, and docplan:go re-checks canAssignTo per task and lists what it refused. Same principle: gate the function, not the UI that reaches it.

5 · What was deliberately not built

  • Team end-of-day for managers. /eod still gives a manager their own report; the CEO gets everyone. A team EOD is a reasonable next step and a separate one.
  • Questions for managers. The question box stays CEO-only in both channels; a manager asking a question in Telegram gets their own work summary, as an employee does.
  • Documents to tasks for managers. Deliberately CEO-only: the planner names people from the whole company, and a manager would get a plan two-thirds refused. Better to not offer it than to offer it broken.
  • Invites for managers. The API says CEO only; the bot matches.

What we have not verified

  • No real manager has used the live bot. The live org chart has nobody with manager or lead; every seeded person reports to the CEO as an employee. The path is proven through the real middleware chain with a mocked Telegram API, not through Telegram itself. The first real use is: CEO promotes someone on People, that person sends /start.
  • The plain-text assignment path for a manager was not exercised — it needs the model to resolve "tell Rahim to…" into an assignee, and the test suite's philosophy is real model calls, which I did not add for this. The per-item check is the same canAssignTo call the tap path proves.
  • A person promoted mid-conversation gets the new role on their next update (the middleware reads the row every time), but a session step started under the old role — e.g. a half-finished assignment — is not re-validated except at the final write, which is the one place it matters.
  • Two CEOs. If the configured Telegram id belongs to one person and access_role = 'ceo' to another, both are CEO in the bot. Nothing prevents it; the People tab's CEO-row rules make it unlikely (A-T38.1, now narrowed).
