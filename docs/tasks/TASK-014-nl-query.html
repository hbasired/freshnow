TASK-014 — Guarded Natural-Language Query

Phase 2 (pulled into demo) · 2026-09-04 · Satisfies SPEC-003 (LLM translates, Postgres computes, gates catch invented numbers) · Ask in plain English, get a SQL-backed answer or an honest abstention. 10 tests + live-verified against real Groq.

What was done

  • query/guard.ts — validateReadOnlySql: single statement, SELECT/WITH only, no write keywords, LIMIT enforced.
  • query/gates.ts — numericSanityGate: every number in the answer must appear in the returned rows.
  • query/answer.ts — answerQuestion: NL→SQL (bounded, validated) → run in a READ ONLY transaction (≤50 rows) → narrate → gate → return the answer with the executed SQL, row count, gate verdict. Abstention is reachable.
  • Tests — guard (5), gate (3), and an end-to-end that proves the gate catches an invented number; plus a live run against the seeded demo DB.

Why it was done

The CEO can ask "how many equipment blockers?" and the model must not read rows and count them — it writes a query, Postgres counts over every row, and the model narrates a small result. Then a deterministic gate runs before anything is shown. If a number can't be verified, the system abstains and shows the SQL rather than guessing. This is the whole thesis of the project made usable.

How it works

question ─▶ LLM: translate → SQL   (validated read-only, LIMIT 50)
                     │
              READ ONLY txn ─▶ Postgres computes ─▶ ≤50 rows
                     │
              LLM: narrate rows → answer
                     │
   numeric-sanity gate: every number in the answer ∈ rows?
        pass → answer + SQL + rowCount + gate verdict
        fail → abstain, show the SQL, never print the number

Live verification (2026-09-04): "How many equipment blockers?" → SELECT COUNT(*) FROM blocker WHERE category = 'equipment' → "There are 2 equipment blockers" (correct). "How many critical?" → WHERE severity='critical' → "1" (correct).

Concepts and techniques used

  • Text-to-SQL with translate-not-compute — the number comes from Postgres, never the model.
  • Read-only transaction guard — set transaction read only makes any write fail at the DB, on top of SQL validation.
  • Numeric-sanity gate — catches "correct query, invented total".
  • Bounded + abstaining — 2 SQL attempts, MAX_ROWS 50, and "I don't have that" is a valid answer.
  • Evidence attached — the executed SQL and row count travel with every answer.

Research findings

The first live run exposed a real limitation: the model wrote WHERE affected_asset = 'equipment' instead of category = 'equipment', returning "0" — and the gate passed, because 0 was faithfully grounded in that (wrong) query. Adding value hints to the schema context (category text[equipment|supply|…]) fixed it. The lesson is recorded honestly below.

What we have not verified

  • The gate catches invented NUMBERS, not semantic query errors. A wrong-but-internally-consistent query (wrong column, wrong filter) passes the gate. Schema hints reduce this; full semantic validation (a second, differently-derived cross-check) is deferred (SPEC-003's cross-validator, task 022).
  • The schema context is hand-curated and hardcoded, not pruned from schema.yaml at runtime.
  • The grounding gate (policy claims must cite a source) is not implemented.
  • The query runs as the service role — per-viewer RLS scoping is wired when the dashboard adds it (so an employee's question only sees their own data).
  • Only simple aggregate questions over tiny seed data were tried; multi-join/complex questions are untested.

Open questions

  • Add a cross-validation step (re-derive the answer a second way) for semantic correctness?
  • Scope the query to the viewer's RLS role at the dashboard boundary (Task 012).
