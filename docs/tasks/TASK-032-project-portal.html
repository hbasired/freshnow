TASK-032 — The Project Portal: a plan, a shape, and an end

2026-09-14 · Phase 5 of the task & project portal plan · migration 0012 · core projects.ts · two SQL views · 16 routes · a portal picker and a project page · 14 core tests + 10 route tests · 26/26 browser checks · 307 tests green

One-sentence summary: A second portal for work that has a reason, requirements with acceptance criteria, weighted milestones, a status log, and risks kept separate from operational blockers — where the percentage is always computed in SQL from the rows, a person's own claim is stored beside it rather than instead of it, and the metrics are the Kanban Guide's flow measures rather than an invented schedule index.

1 · The two decisions that carry the design

DecisionWhy
The existing task table is the unit of work for projects too — task.project_id and task.milestone_id, not a parallel project-task system. Everything Phase 3 built (steps, progress with a named source, relations, resolution) applies to project work unchanged, and a person's "My work" stays one list whichever kind of work it came from. A second task table would have meant two of every rule, drifting apart.
Progress is a view, never a column. project_progress computes it from milestone weights, or the tasks' own evidence-based percentages when there are no milestones — and progress_source says which. A stored percentage is a number somebody typed once and nobody updated. A view cannot go stale. And the number is never readable without its basis.

What a person may type, and where it goes

Exactly two things on a project are human judgements rather than arithmetic, and both are quarantined:

  • health (green/amber/red) — set by a person, always with a mandatory note and a timestamp, because whether a schedule slip is worrying is a judgement the data cannot make.
  • project_update.pct_reported — "where we think we are". Stored in the status log next to the computed figure, never replacing it. The API returns the computed number with the claim, the audit row records both at the moment the claim was made, and the UI writes the gap out in words: "You said 80%; the work shows 25%."

2 · Design references

ChoiceReference
Requirements prioritised MoSCoW, including won'tMoSCoW's own definition. "Won't" is the half people skip; writing down what is out of scope is what stops it being argued back in later.
Every requirement carries acceptance criteriaA requirement nobody can test is not a requirement.
Per-milestone progress, weightedLinear computes progress per milestone specifically so critical work cannot hide inside an aggregate. Weights mean a two-month milestone need not count the same as a two-day one.
Flow metrics: WIP, Throughput, Work Item Age, Cycle Time — cycle time as percentiles (50/85/95), never a meanThe Kanban Guide (v2025.5). The distribution is skewed; the mean of a skewed distribution describes nobody's experience. Work Item Age is the only leading indicator of the four.
No SPI, CPI, earned value, velocity or burndownThey need a time-phased cost baseline FreshNow does not keep. Inventing one would be a fabricated number — the exact failure HONESTY-AND-ACCURACY.md exists to prevent.
project_issue is a separate table from blockerA broken chiller is an operational problem with a response window in minutes and an escalation ladder; "the supplier may slip" is a risk reviewed weekly. One table would give one of them the wrong urgency and would corrupt the blocker SLA statistics.

The milestone gate

Marking a milestone done while tasks under it are open is the single most common way a project reports itself green while being late. The core function refuses it; the route answers 409 with the count; the UI then asks "2 task(s) under this milestone are not finished. Marking it done anyway is recorded as forced." — and force: true writes forced and openTasksAtTheTime into the audit row. Nothing is prevented; it is simply impossible to do it quietly.

What we have not verified

  • No real project has ever been run through this. Every fixture is invented. The shape follows established practice, but FreshNow has not told us what their projects actually look like — whether they think in milestones at all, and what they would call the stages.
  • The 7-day staleness threshold is assumed (STALE_PROJECT_DAYS), as is reusing the task board's 30-point "behind" threshold for projects.
  • Weights default to 1. Unless somebody sets them, the weighted rollup is an unweighted count of milestones — correct, but not the benefit the column exists for.
  • Project alerts do not yet use the Phase 4 event catalogue. They write outbox rows directly (both channels, with a reason), so a person's notification_pref rules do not apply to project news. That is deliberate — someone who silenced task assignments has said nothing about project news — but it means project notifications currently cannot be turned off. Named here rather than implied.
  • There is no UI to create a task directly inside a project. Work is created in the task portal and filed into a project (PATCH /dashboard/tasks/:id/project, tested); the project page only shows it. The Work section says so.
  • The project sweeps have not been observed firing on a real timer — they are tested by direct invocation and run hourly in the worker, but no hour has elapsed with a genuinely overdue project in the live database.
  • Cycle time counts from started_at, falling back to created_at. For tasks created before Phase 3 there is no started_at, so their cycle time is measured from creation and will read long.
  • The bot knows nothing about projects. The whole portal is dashboard-only.

Security and honesty

  • Both views are security_invoker = true. Without it a view is a hole straight through RLS — the single most common way row security is accidentally defeated. The RLS tests query through the tables the views read, and a stranger sees nothing.
  • Six new tables, all enable + force RLS, visibility via app_can_view_project(): members, plus anyone who may see the lead or sponsor, plus the CEO.
  • Writes check permission in the route before calling core, with a test for each refusal — the same pattern as every phase since Phase 1.
  • No model touches any of it. Every number on the project page is SQL over every row.
  • Nothing here scores a person. Flow metrics are about work items, not people; there is no per-person throughput, and there must not be.
  • One migration was corrected in place (the view counts returned bigint, which reaches JavaScript as a string). 0012 had been applied only to the local databases that day, and the views are now dropped-then-created so a type correction can apply at all — CREATE OR REPLACE VIEW cannot change a column's type. Stated because "never edit an applied migration" is a project rule and this is the exception being taken knowingly.
