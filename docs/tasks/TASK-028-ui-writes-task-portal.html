TASK-028 — The Dashboard Can Create Work (Task Portal, Phase 1)

2026-09-14 · Phase 1 of the task & project portal plan · 5 new write routes, 2 document routes, form primitives, three tab rewrites · 14 new API tests · two real-browser runs (19 + 10 checks) · one Telegram message per browser assignment actually delivered

One-sentence summary: Everything the CEO does in Telegram — assign work, add a person, turn a document into tasks, acknowledge a blocker — and everything an employee does — report a status, raise a blocker in their own words — can now be done in the dashboard, and it lands in the same tables, the same audit trail and the same Telegram delivery as the bot, because the UI calls the same core functions the bot calls.

1 · Why

The dashboard could read everything and write almost nothing: its only actions were "generate reports" and "ask a question". The plan approved on 2026-09-14 makes the UI a second channel with one database and one outbox behind it, then adds depth (progress, problems, reporting lines, alert routing) and a project portal. This is the first phase.

2 · Design rule that shaped every line

The UI never calls Telegram, and never re-implements a rule. A route is a Zod-validated shell over assignTask, recordTaskUpdate, createTask, acknowledgeBlocker, planDocumentTasks — the functions the bot already calls. Telegram delivery happens because assignTask writes an outbox row and the worker delivers it. "In sync" is not a feature; it is the absence of a second code path.

Writes are authorised in the handler, not by Postgres. Core writes run as the BYPASSRLS service role, so a permission check the route forgets is a permission nobody enforces. Every check has a test that proves the refusal.

The document limitation, stated

Attachments in this system are Telegram file_ids, not bytes. A browser upload has none, so a document read in the dashboard produces tasks — with the file name in each note as provenance — and the file itself is not forwarded. The route returns fileForwarded: false and the card says so before the user presses anything. Forwarding needs the worker to upload bytes to Telegram and store the returned id: planned, not built.

4 · What the browser found that the tests did not

Every body-less POST from the browser returned 400

The client always sent Content-Type: application/json. Fastify refuses an empty body that claims to be JSON. So Acknowledge failed in the browser — and so did the existing Generate end-of-day reports button, which nobody had pressed from the React app before. The route tests passed because inject sends no content-type. Fixed in the client; recorded as G70.

The document confirmation toast was never visible

After Create, the card resets to the upload form, and the success toast lived inside the review branch that had just unmounted. The user would have created three tasks and seen nothing. Moved the toast outside the branch.

Two test-harness mistakes, for the record

"Task left the list" checked the page text, and the toast quotes the title. A shared busy flag briefly disables every button on a tab, and clicking a disabled button passes silently. Both were the harness, not the app; both are fixed in the harness.

What we have not verified

  • Phone use of the new forms. Every browser check ran at 1280 px on this laptop. The forms use wrapping flex and the phone-width layout was reasoned about, not seen.
  • A real PDF through the browser route. The document tests and the browser run used text files; PDF extraction is covered by the existing core tests, and the route calls the same function, but the multipart → PDF path has not been exercised end to end.
  • The assignment rate limit from the UI. Enforced (100/hour) and unit-tested in core; not driven to the limit through the route. The bot's assignment path remains unbounded — recorded, not implied.
  • Behaviour when the recipient has no Telegram. The picker warns, and assignTask still queues a row with a null chat id, which the worker will fail and retry. That is the pre-existing behaviour; a cleaner "held until they join" state belongs to the alerting phase.
  • Managers. Every write is CEO-gated or self-only. The manager and department-lead rules you chose are Phase 2, and the routes say so in their comments rather than pretending.

Security

  • Six refusal paths are tested (task for a colleague, assignment by an employee, report on a colleague's task, acknowledge by an unrelated employee, document plan and apply by a non-CEO). These are the only defence for writes.
  • The upload runs the same byte-level safety gate as the bot before any parser sees the file, inside the same size cap; an executable renamed .pdf is rejected with the same reason text.
  • Prompt-injection scanning and spotlighting apply unchanged; the response tells the CEO when instruction-shaped text was found and ignored.
  • The three probe Telegram messages sent to Hemanth's phone during verification are real deliveries; the probe rows were removed afterwards, the audit log was left as it was.
