One-sentence summary: The audit found that a chat message like "ask Ahmed to count stock" was assigned immediately to whichever person the model picked — with two Ahmeds, a coin toss nobody would see — so every "who" decision now goes through one deterministic check (the name as written must fit exactly one person, by whole words, or the sender is asked); it also found that identifier placeholders made two phone numbers indistinguishable and left "[phone]" in the assignee's task, and that employees' words survived retention and erasure inside the replay trace — all three are fixed and tested.

The question asked: does routing stay correct when prompts are cleaned?

Names were never removed from prompts — by design (D152): the model has to read "Rashid" to route to Rashid. What is removed is phone numbers, emails, Emirates IDs, IBANs and card numbers. The audit traced every path that decides who and found the real risk was elsewhere:

The matching rule (people-match.ts)

  • Words, not letters: every written word must equal a word of the person's name, or be the start of one if it has 3+ letters ("Rash" → Rashid). "Ali" ≠ Khalid.
  • A full-name match wins outright ("Ahmed Ali" means Ahmed Ali). Case, accents, punctuation and a few honorifics (Mr, ji, bhai …) are ignored (A-T52.1).
  • Strict on purpose: "Sara" with a Sara and a Sarah on the books, or "Jose" with a José and a Joseph, is asked — a mis-sent task reaches a real phone; asking costs one tap.
  • Pure and deterministic: the same message routes the same way every time, and the grounding functions are exported so routing is tested and replayed without a model.

How it was verified

  • 14 matcher tests and 10 routing tests written from the rules (two Ahmeds; the name beats the model; "Ali" not Khalid; another script → suggestion only; several people in one message each checked on its own; an out-of-range index is nobody); a real-bot test with two team members named Ahmed (asked with only their two buttons, nothing created; "Ahmed Khan" then creates exactly one task for him).
  • Placeholder tests: two numbers stay two, the same number keeps its placeholder across messages, the answer is restored at any depth, an invented placeholder is left alone; and end to end through llmComplete with a stand-in provider that reads the placeholders from the prompt as a model would.
  • Retention: a trace older than the window loses the words and keeps the fact; a recent one is untouched; erasure clears that person's traces.
  • Full suite 591 passing; typecheck clean (root and dashboard); 37/37 + 13/13 browser checks.

What we have not verified

  • That a live model fills named_as reliably. The 8 real-model tests could not run here (no route to Groq). If a model leaves it empty, chat assignments are asked about rather than guessed — safe, but more taps. Run pnpm test on the laptop with a real key.
  • Names written in Devanagari or Malayalam script never match by spelling (display names are in Latin script), so they always go to "did you mean …?". Not measured on real messages.
  • The honorifics list (A-T52.1) and whether the strict prefix rule asks too often in practice.
  • The legal ground per processor (R2) — a lawyer's question, not code's; nor whether the PDPL's executive regulations change any rule.
  • The owner label on the dashboard's document screen with a real plan — it needs a model call; the label logic is typechecked, not seen in a browser.
  • Replay of a trace after the retention sweep is, by design, no longer possible.
