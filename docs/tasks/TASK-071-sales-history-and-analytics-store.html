Why it was done this way

Only checked days

The 10-minute sync reads overlapping short windows; it cannot say a day is whole. A daily check (04:00 Dubai) or a backfill reads a whole day again and compares it with Televend's own count. Only those days are built. A day not built is "not read" in every figure, never "nothing sold". Yesterday therefore arrives in the store about an hour after its morning check (R15.6).

Rebuilt, never edited

A late sale stored after a build changes the day's input (the count read, the newest sale stored), and the next run builds the day again: its rows are replaced in one transaction and the earlier run stays in analytics_run. So every figure traces to a run, and a run can be repeated to the same answer (CLAUDE.md rule 3).

Where the machine stood, not where it stands

Machines move, and a move gives the machine a new Televend record (asset 796 has had four, G160). Each sale carries its record's name and region at the time, and the store keeps those of the day's last sale. Categories are not stored per day: FreshNow's corrections must reach back over the history, so they are applied when the store is read (D257).

Televend's totals where the list stops

Televend's itemised sales list reaches back about 200 days, but its own daily count goes further (VF87). The count is kept as it is, one figure per day for the fleet: enough for a long trend, not for machines or categories. Nothing is invented for the missing detail.

Not built here

  • A table per category per day (the plan's wording): categories are worked out at read time, for the reason above.
  • Any chart of the long history — the day totals are stored, not shown yet (TASK-075).
  • A nightly schedule for the backfill: it was run by hand. The daily check keeps each new day; the sales list's start moves forward as days age out (VF87), so there is nothing older left to copy.

How it works

daysToBuild asks Postgres for whole Dubai days with a complete daily-check or backfill run of the sales stream, measures each day's input inside Postgres (how many sales, the newest synced_at — G202), and returns those never built or built from different input, oldest first. buildSalesDay takes an advisory lock for the day, reads Televend's count from the newest complete run, deletes the day's rows and inserts them again from tv_vend by one insert … select per table, and records the run with agrees = (sales read = Televend's count). All counting is Postgres's; the TypeScript only chooses days.

Research findings

  • How far back Televend keeps sales, by read-only probes through the MCP tool (VF87): the list held 31 Mar 2026 and later, not 20 Mar or earlier, while the daily count reaches further.
  • Televend's day count ignores the time of day and includes the end date (G147); only whole days are compared, sent as the last second of the last day.
  • The sales list includes both ends of a window (found 20 Oct, G215), while the day count does not take the next day's 00:00:00 sale.
  • Sale records spell a region differently from the machine list ("Other Stations" against "Other stations", G211).

What we have not verified

  • The sales list as a rolling window: whether Televend drops a day from the start each day (VF87) is not watched yet. The store keeps what was copied either way.
  • 25 March: only part of the day is in the list (719 sales read); it stays out of the store.
  • Day totals before October 2025 were not asked for; how far Televend's count reaches is not known.
  • Speed at a year's volume: a day builds in well under a second today (about 1,500 sales); a year of rebuilds was not timed.
  • The MCP server used by Claude Code was still running the reader from before the midnight fix; it picks the fix up when it is restarted.
  • Replay of a run is "build again and compare"; no test replays a stored run against changed sales on purpose.
