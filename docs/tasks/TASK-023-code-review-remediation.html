TASK-023 — Full Code Review & Remediation

2026-09-09 · /code-review high packages/ over ~7 000 lines · 15 findings, 15 verified real, 15 fixed · 197 tests green

One-sentence summary: A full review of the codebase found fifteen defects — including an outbox that could starve itself so no message was ever delivered, executable attachments passing the safety gate as "safe", a row cap escapable by a subquery, and a rate limiter that counted nothing — every one verified against the running system before being fixed.

Method

The repository is not a git repository, so there was no diff; the review took packages/ as an explicit target. Every finding was reproduced against the running system before any code was changed — an agent's report is a hypothesis, not a result. All fifteen held up. No false positives.

Findings and fixes

1High The outbox could starve itself. The relay claims the oldest batchSize pending rows; a failing row stayed pending and was re-claimed on the next poll, so batchSize bad rows filled every batch forever and no other message was ever delivered. Telegram's retry_after was captured and then discarded. Migration 0006 adds next_attempt_at; the relay only claims due rows; failures back off exponentially (2s→5min) or honour the server's own retry_after. Test: one poisoned row + two good ones at batchSize: 1, both good ones delivered.
2High Executables passed the safety gate. .bat, .js, .ps1, .sh, .vbs, .msi, .lnk, .apk have no signature we check, so they returned verdict: safe, mayForward: true — a working payload forwardable to an employee's phone. Reproduced directly. Extension-based refusal, precisely because byte inspection cannot help. An unidentifiable format is now suspicious (readable, never forwardable) rather than safe.
3High Every day window was four hours out. The container's Postgres runs Etc/UTC, so '2026-09-09'::date meant midnight UTC — 04:00 Dubai. The previous fix corrected which date string we ask for, not what it means. connection: { timezone: "Asia/Dubai" } on both pools — one place, not 21 queries. Verified: the window now starts at 2026-09-08T20:00Z, exactly Dubai midnight.
4High The rate limiter counted nothing. document.planned was logged as actor: "system" while the limiter counts employee:<id>, so the 20/hour cap could never fire. The unit test passed because it wrote the audit rows itself. Attributed to the person; uploadedBy threaded from the bot.
5Med MAX_ROWS was escapable. The guard accepted any limit n in the text, so a LIMIT in a subquery suppressed the outer cap and Postgres materialised every row. Wrap rather than append: select * from (<sql>) as bounded_result limit 50. A subquery cannot escape its own parentheses.
6Med Anyone could acknowledge a blocker. The ack: callback had no role !== "ceo" check, unlike every other CEO action — so an employee could permanently suppress escalation of their own blocker. Role check added, with an alert explaining why.
7Med "Which task?" silently ate the reply. When an employee typed instead of tapping, the handler filed the held text and discarded what they had just typed — the comment claimed the opposite. Their answer now resolves against their open tasks; the original words are still filed.
8Med Photos never reached blocker reports. processNote never took the held files, so a photo sent with a fault description stayed on the session and surfaced attached to whatever the person did next. takePendingFiles called on the update the words belong to.
9Med Markdown 400s made the bot look dead. An odd _ in a filename — q3_report_final.pdf — makes Telegram reject the whole message, so the CEO saw "Reading…" and then nothing, with no error visible anywhere. escapeMarkdown() on every filename, title, summary and name.
10Med The same photo delivered once per task. pendingFiles was passed inside the multi-item assignment loop, so "tell Rashid X and Priya Y" sent the picture twice. Files taken once, attached to the first item — matching the document path, which already got this right.
11Med A typo could assign work to the wrong person. Name resolution was first-substring-match with no ambiguity check — with a Sara and a Sarah, whoever sorted first won, silently. Exact match wins; otherwise a unique match is required, and an ambiguous one lists the candidates and asks.

Two findings that deserved a judgement, not just a patch

The escalation timer

armEscalation lives in the worker; the code that routes a blocker lives in core; core must not depend on the worker. That dependency direction is why it was never wired — not an oversight so much as a design that never met itself.

Rather than invert package dependencies late in the day, the sweep interval went from 5 minutes to 60 seconds. Escalation is now at most a minute late instead of five, which for a 15-minute critical SLA is the difference that matters, and it costs one indexed query a minute. The timer path also gained the same "already escalated?" guard the sweep has, so it is safe if it is ever armed. Wiring it properly means moving the queue into core — recorded as not done rather than implied. The misleading "the escalation timer is cancelled" message is gone.

Dashboard authentication

Adding a viewer=ceo check would have been theatre: viewer is a query parameter anyone can set. The honest position is that this demo has no authentication at all, on purpose, so a phone can reach it.

DASHBOARD_TOKEN is a real gate: set it and every /dashboard/* request must carry it (?k= or X-Dashboard-Key, constant-time compared); leave it unset and the demo behaves exactly as before. A gate that can be switched on is worth more than a comment saying one is needed, and the default keeps the trade-off visible.

A defect the fixes themselves surfaced

Two tests failed after the fixes, and both were encoding the old buggy behaviour rather than catching a regression — "keeps an existing LIMIT" asserted the exact string that made the cap bypassable. They were rewritten to assert the property (the result is capped) rather than the implementation.

A third failure was real and unrelated: the outbox tests assert on counts, but the relay claims from the whole queue, so any other suite's leftover pending row was silently counted. Fixed with a beforeEach that empties pending rows.

What we have not verified

  • None of these fixes has been exercised from a real phone.
  • The dashboard remains open by default. DASHBOARD_TOKEN is unset, so on an untrusted network this is a real exposure — the gate exists, it is simply not switched on.
  • The escalation timer is still unarmed. Escalation latency is now bounded by the 60s sweep, which has not been measured under load.
  • The dangerous-extension list is a denylist, and denylists are never complete. A format not on it that some phone treats as executable would still pass.
  • The review covered packages/ only — scripts/, migrations/ and the docker configuration were cross-referenced but not reviewed line by line.
  • Carried over: voice accuracy unmeasured; llm_call.cost_usd reports 0; the NL-query box still runs as the service role rather than under the viewer's RLS context.
