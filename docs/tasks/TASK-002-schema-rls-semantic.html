Phase 1 (demo) · 2026-09-04 · Satisfies SPEC-000 R4/R6 (deterministic routing), R9/R10 (append-only audit), and the CLAUDE.md database-schema + semantic-layer rules · Adds the core Postgres schema, row-level security, the hand-maintained semantic layer, and a real test harness. 17/17 tests green against real Postgres.

What was done

  • Row-Level Security, default-deny on all 15 tables, with policies for an RLS-enforced app role (freshnow_app) and a bypassing service role (the owner/superuser). audit_log is append-only (no UPDATE/DELETE granted).
  • Degenerate routing seed — a DEMO CEO employee and 5 routing_rule rows all resolving to the CEO (verified: distinct_resolvers = 1).
  • semantic/schema.yaml — every table and key column documented in business language, with FK purpose strings including the self-referential employee.manager_employee_id and the twice-joined blocker.raised_by / assigned_resolver.
  • packages/core/src/roles.ts — deterministic resolveRole(userId, ceoUserId); meta.ts — PROJECT_NAME, IS_DEMO.
  • Test harness — vitest.global-setup.ts creates and migrates a throwaway freshnow_test database; vitest.setup.ts points the db layer at it. scripts/migrate.ts applies migrations to the demo DB (tracked in schema_migrations).
  • The DB access layer packages/core/src/db.ts and the acceptance tests (db.rls.test.ts, semantic.test.ts, index.test.ts) arrived as an externally-supplied test suite; this task implements everything they assert (see Research findings).

Why it was done

Determinism & audit (SPEC-000 R4–R10). Routing must be a lookup, not a model call, and every state change must be traceable and unforgeable. The routing_rule table is that lookup (degenerate → CEO for the demo, but table-driven so real routing is a later data change, not a rewrite). audit_log is append-only so "who changed what" cannot be rewritten.

RLS as the isolation boundary (constraint: an employee must never see another's tasks). Enforcing this in the database — not the application — means a bug in a handler cannot leak another employee's rows. Research confirmed the critical footgun: if the app connects as the table owner, policies are silently ignored. So the app connects as a non-owner role and the worker uses a bypassing service role.

A throwaway test database. CLAUDE.md forbids mocking the DB in integration tests. Tests run against real Postgres, but in a separate freshnow_test database so running the suite never wipes demo data shown to officials.

How it works

Two roles, one boundary. The app connects as freshnow_app (login, non-owner, no BYPASSRLS) so RLS applies. The worker/migrations connect as the owner/superuser, which bypasses RLS by design.

request ─▶ withContext({employeeId | isCeo}, fn)
             └─ sql.begin(tx =>
                  set_config('app.employee_id', <uuid>, true)   ← is_local: scoped to THIS txn
                  set_config('app.is_ceo',     'on'|'off', true)   ← pooling-safe, no leakage
                  fn(tx))                     policies read current_setting(...) per row

The policy shape (task_update shown): read/insert only your own rows; the CEO context sees all.

using       (employee_id = app_current_employee() or app_is_ceo())
with check  (employee_id = app_current_employee() or app_is_ceo())  -- blocks inserting as someone else

Append-only audit is enforced twice: a CEO-only SELECT policy + an INSERT policy, and UPDATE/DELETE privileges are revoked from the app role, so a tamper attempt fails at the privilege layer.

Tests attack the boundary rather than assert the implementation: they try to read another employee's rows, insert across employees, and UPDATE the audit log — and confirm Postgres refuses.

Concepts and techniques used

  • Row-Level Security with a non-owner login role — isolation enforced by Postgres, not the app.
  • Transaction-local GUCs via set_config('app.*', …, true) — the parameterised form of SET LOCAL, scoped to the transaction so a pooled connection cannot leak one user's context into the next request.
  • WITH CHECK — separates what you can read (USING) from what you can write, blocking cross-employee inserts.
  • Append-only by privilege + policy — defence in depth on the audit log.
  • The semantic layer — a hand-maintained meaning map; FK purpose strings spell out self-joins a model cannot infer from types.
  • Deterministic role lookup — resolveRole is a pure bigint compare, never a model call.
  • Forward-only migrations with a schema_migrations ledger; a throwaway test database instead of DB mocks.

Research findings

Searched at task start (2026-09-04):

  • postgres.js RLS pattern — sql.begin(tx => …) with set_config(…, true) is the documented transaction-scoped approach; the true flag is what makes it pooling-safe. Adopted as-is in db.ts.
  • RLS + roles — PostgreSQL docs and multiple production write-ups confirm: superusers, BYPASSRLS roles, and table owners bypass RLS; the fix is to run the app as a non-owner role. This directly shaped the two-role design.
  • vitest globalSetup — runs once before the suite; the right place to create/migrate a test DB. Adopted.
  • Externally-supplied acceptance tests. Four files (db.ts + three test files) appeared in packages/core/src that were not authored here; they encode exactly the T2/T6 behaviour in the plan. Per instruction, this task was built to satisfy them (TDD-style). Only their relative-import extensions were adjusted to compile under NodeNext; their logic was left untouched.

What we have not verified

  • RLS correctness is proven for the tested tables and contexts; policies on the untested tables (escalation, assignment, outbox, invite, voice, run_trace, llm_call, job_run) are reasoned, not exercised by a test yet.
  • Behaviour under a real connection pool with concurrency is untested (tests run files serially); the transaction-local guarantee is taken from documentation, not measured under load.
  • The migration ledger has only ever applied one migration; multi-migration ordering/rollback is untested.
  • pgvector is installed but no vector column or index exists yet — its availability is assumed from the image, not exercised.
  • The freshnow_app password is a dev-only literal in the migration; production secret handling is not addressed.
  • The schema's categories, statuses, and the degenerate routing are synthetic placeholders — real values depend on company answers A7–A9.
  • Whether the demo DB's schema should later be reset/re-seeded (vs. accumulate) is not decided.
