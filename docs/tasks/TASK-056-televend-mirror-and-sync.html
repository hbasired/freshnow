Why it was done this way

A mirror, not live calls from every screen

The Operations portal, the reconciliation rules and the app need Televend's data joined with our own stock, cash and visits, at the speed of a database query, and still available when Televend is slow or down. Televend is read on a schedule, paced at one request per second; screens read Postgres.

Never twice, never "probably complete"

  • Vends are keyed on Televend's vend id; events on the event id (upserted: an alarm resolved later updates its row); refills — which have no id — on machine asset number + time to the second + machine column + action + quantity, so the same refill from the API and from an export is one row.
  • A stream's cursor moves only after a complete read. Incremental windows overlap the last read (30 min vends, 60 min events) because telemetry boxes that were offline upload late with their original timestamps.
  • Once a day after 04:00 (after the night shift) yesterday is re-read whole and its vends compared with Televend's own whole-day count — the only way a day is marked complete (G147). A day that will not complete is tried at most three times.

A bug the exports caught (G159)

The first refill key (asset number + second + action + quantity) silently dropped a genuine refill: a two-column machine logged two fills in the same second with the same quantity, one per product. The backfill's "65 read, 64 new" for 11 Oct prompted the check against the CSV, which showed the two rows differ only in column and product. The column is now part of the key; the stored rows were re-keyed and the affected days re-read (the dropped refill came back); a test covers the case. The lesson stays in the design: a backfill compared with an independent source catches what unit tests written from assumptions do not.

A second gap the same comparison caught (G160, G161)

After that fix, three refill rows were still only in the export — all one machine, on 4 and 6 Oct. The machine had moved to a new site: Televend gave it a new record and disabled the old one. The old record keeps its refill log, including the row of the machine being emptied before the move, but the machines list no longer shows its last refill — and a whole-day read asked enabled records only. A past day now asks every record, enabled or not (221 instead of 87 requests a day, D193): nothing in Televend's list says which disabled record was live on a given day, so pruning would be a guess. A record that turns disabled between two syncs has that day's log read at once. The comparison also named an unmapped Televend code — refill type 4 from source 3 is the export's "Removed / Televend" — and the one stored row was corrected and re-keyed before the re-read, so it is not stored twice.

Running the tests stopped the sync (G163)

While watching the 10-minute cadence, the sync stopped. The test suite used a throwaway Postgres but the developer's live Redis database, because both queue modules read only host and port from REDIS_URL. An opt-in email test starts the background jobs; with Televend settings cleared under tests, that start removed the live televend-sync schedule, and its teardown removed the email schedules — and a running worker only registers schedules when it starts. Now one redisConnection() reads the whole URL including the database number, and the suite runs in its own database (15) and refuses to run in the live one. Redis's own command log confirmed it: the same opt-in run sent all its commands to database 15, and the live schedules survived.

Concepts and techniques used

  • Change-data mirroring with high-water marks — a cursor per stream that only moves after a complete read.
  • Overlapping windows for late-arriving data — re-read a margin; idempotent keys make the overlap free.
  • Reconciliation against the source's own totals — completeness is measured, not assumed.
  • Upsert with a change guard — update only when something changed, so last_seen_at and counts mean something.
  • Physical asset vs system record — one machine, many Televend records over time (placements), the human key (asset number) kept.
  • Bounded retries at two levels — inside a run (connector) and across runs (next schedule; max 3 daily-check attempts).

Research findings

  • Televend serves whole-day vend counts back at least a year and events back to at least April 2026 through the web endpoints (VF62) — history can be backfilled from Televend itself; the portal exports remain a fallback.
  • The official Data-Streaming API keeps 7 days (TASK-055 research) — the history must come before the switch to it.

What we have not verified

  • Weeks of unattended running: Keycloak session end and re-sign-in, Televend outages against the circuit breaker, disk growth of raw.
  • That 30/60-minute overlaps catch every late upload (A-T56.1) — the daily check catches the rest, but only for yesterday.
  • The official-API transport in the pipeline (no credentials).
  • Retention and erasure of staff names copied from Televend (A-T56.2) — waits for the people mapping (TASK-057) and the notice update.
  • How far back Televend serves history (earliest date not searched; refills and events older than April 2026 untested).
  • Load on the shared VPS: measured only on the laptop.
  • Refill codes 2 and 3 have never been seen; rows carrying them are stored as "unknown" and must be re-normalised and re-keyed when their meaning is learned (G161).
  • The enabled → disabled flip on a live machine move: covered by a test only — no machine moved while the worker was watching.
  • The partial-failure paths (G165) against the real Televend — tested with a scripted source only; no real failure happened while watching.
  • The test-database guard's "same server and database" branch: refusing on the name fired first in the only safe check.
  • A daily check that reads every machine record's refills has not run on its own yet: 14 Oct was checked before the G160 fix (and re-read by hand afterwards); the first is due after 04:00 Dubai on 16 Oct.

Open questions

  • How much history should be loaded (vends exist back to at least Oct 2025; a year is ≈ 10,000+ paced requests per stream)?
  • Retention for Televend copies in our database (sales are business records; names are personal data).
