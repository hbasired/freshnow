Why it was done this way

Why the 60% disappeared

Two causes, both in code that existed. The Pending tile counted status reports made today and jumped to the Overview it was already on, so it went nowhere; and the report rows carried no percentage. Underneath that, recomputeProgress replaced a person's own figure with the status default (10% / 50%) at the next status tap, and a "60% done" typed into Telegram was never read as a number at all (G142). The fix keeps the person's figure until there is better evidence (counted steps) or the task finishes, reads a stated percentage with a pattern — a number the person typed, never a figure a model produced (CLAUDE.md rule 2) — and gives Pending a page of its own that shows the figure with who reported it, when, and their words.

Why a choice per assignment, and why it can be refused

Options: (a) a global switch — already exists (Alerts → Channels) and cannot express "this one by email"; (b) change the person's preferences — wrong owner, and it would silently change every future message; (c) a choice for this message only — chosen. The choice decides which channels; facts still decide whether each can carry it, so Email is greyed out for someone with no address rather than accepted and dropped. Refusing when nothing can reach the person keeps an invariant: no task exists that its owner was never told about. The form sends a choice only when it differs from the person's usual, so the record (notify_channels) distinguishes "the CEO chose" from "nobody chose".

Why email now assigns directly (a change to D166)

TASK-053 made every work email a proposal. The user asked for email to behave like Telegram, where a message naming exactly one person assigns at once (D161). The same rule now applies, in code: the model reads the jobs; who each is for is decided by the name check, an email address, or the email's own recipient. Anything uncertain still waits for a person, and the whole email waits — never half of it. The sender must still be authenticated (SPF/DKIM/DMARC or the account's own Sent mail), allow-listed, active, consented, allowed to give that person work, and under the hourly limit.

Why read the Sent mailbox

The research for this task found that Gmail does not put mail you send to your own alias in the Inbox — only Sent and All Mail. The TASK-053 poller read only INBOX, so the CEO emailing the +freshnow alias from the same account was very likely never seen (A-T53.2, now corrected). This is flagged rather than silently followed: the fix (read \Sent too) was reproduced against a real IMAP server, and the Gmail half stays an assumption to confirm on the laptop.

Why consent by email, not by the CEO

A person added with only an email has no Telegram button and no app login, so before this they could never agree — and the outbox would hold their work for ever. The CEO cannot consent for them (PDPL: the data subject's own act). The notice goes to them by email with the hash of its exact words; an explicit "I AGREE" reply, from their authenticated address, in the thread of that notice, is recorded. A bare "yes" is not accepted. Whether this is sufficient is a lawyer's question (A-T54.2).

Concepts and techniques used

  • Intent vs record. assignment.notify_channels is what was chosen; the outbox is what was sent. Keeping both lets a skipped channel be explained later instead of guessed.
  • One function for "can it reach them". The form's greyed-out chip and the sender use the same unreachableReason / usualChannels, so they cannot disagree.
  • Deterministic ownership. Name-unique match, explicit address, or sole recipient — decided in code, recorded per task in the audit row (ownerBy), replayable without a model.
  • RFC 6154 special-use mailboxes. Find Sent by its \Sent flag, never by a localised folder name.
  • IMAP OR search — To or Cc in one server-side query (imapflow builds the binary OR tree).
  • Consent bound to text. The notice hash travels with the email and is checked when the reply arrives, so agreement is to the words that were shown.
  • A number counted once. Tiles come from SQL; each page filters with the same definitions, so a tile and its list agree.
  • State in the URL. A third hash segment carries the page's filter, so lists are bookmarkable and Back works on a phone.

What we have not verified

  • Gmail itself — unreachable from the build machine. The Sent-mailbox and Cc paths ran against Dovecot only (A-T54.1, A-T53.2). First real check: Act E5 in EMAIL-DEMO-GUIDE.md on the laptop.
  • That a Gmail "Reply all" keeps the alias in Cc and the original Message-ID in In-Reply-To — believed standard, not observed.
  • Any real model — every planner call in tests used a stand-in; the live model's reading of real CEO emails ("named_as" filled reliably) is unmeasured. A model that fills named_as with a name for an email addressed to one person would make that email a proposal instead of an assignment (safe, but less convenient).
  • PDPL sufficiency of consent by email reply — a developer's reading (A-T54.2).
  • Telegram delivery of a chosen channel — tests use the outbox; no real Telegram send was made in this task.
  • Web push as part of "App" — covered by existing tests; not re-run on a phone in this task.
  • Non-English percentages — statedPercent reads ASCII digits with %, percent, per cent. Devanagari or Malayalam digits, or "sixty percent" in words, are not read (the words are still kept and shown).
  • Scale — /dashboard/people/reach calls canAssignTo once per visible person for a manager (bounded at 500); unmeasured with a large org. The open-tasks query gained correlated subqueries; unmeasured on large data.
  • Withdrawal by email — an email-only person withdraws by asking the CEO (People → Has left… → Withdrew consent); there is no "reply WITHDRAW" path.
  • Signed-in mode (Supabase JWT) — the browser run used demo mode; the new routes use the same resolveViewer as the rest.
