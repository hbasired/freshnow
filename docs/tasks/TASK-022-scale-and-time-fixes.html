TASK-022 — Scale, Confirmation Naming & Company Time

Phase 2 · 2026-09-09 · Satisfies CLAUDE.md rule 4 (bounded) and the style rule "store UTC, render Asia/Dubai" · Follows the first live end-to-end run of the document pipeline

One-sentence summary: A screenshot review confirmed the document pipeline works end to end and exposed two real defects — status confirmations that never named the task, and every displayed time being four hours wrong — then the bot was moved from one-update-at-a-time to concurrent processing with per-chat ordering and a measured cap on model calls.

What the screenshots confirmed

The document pipeline ran end to end for the first time, verified against the database:

  • 4 tasks created from the PDF, all routed, delivered as 4 separate "New task from the CEO" messages
  • The file was not forwarded — the default held
  • The two names the document invented (manvanth, atif) were flagged and resolved by the CEO's tap, not guessed
  • Blocker detection fired on ordinary free text: "Did not go to the warehouse as travel was not possible" → high logistics problem, CEO alerted

Defect 1 — "Recorded as done" never said which task

The employee reported that a task they had marked done was still showing. The database was right and the interface was wrong:

TaskStatusNote attached
Assign tasks from PDFdone"The demo finalization is complete and ready for demonstration."
Build finalized DEMO platform…opennever reported

The /log board posts one card per task. Tapping a button puts the confirmation at the bottom of the chat, far from the card pressed, and the text said only "Recorded as done. Anything to add about this task?" — so the employee tapped the first card, believed it was another, and their note about the demo platform was filed against "Assign tasks from PDF".

Every confirmation now names the task: ✅ Recorded as done: "Assign tasks from PDF". Cheap to fix, and it was producing genuinely wrong records — a note about one job attached to another, and a task the CEO would see as untouched while the employee believed it finished.

Defect 2 — every displayed time was UTC

CLAUDE.md says "Store UTC, render Asia/Dubai." Only the first half was true. The employee was shown 05:11 for a message their own phone stamped 09:11 — four hours out on every timestamp this system has ever displayed, which makes an evening report look as though it was filed before dawn.

Worse than cosmetic: new Date().toISOString().slice(0,10) was used for "today" in the end-of-day report and the dashboard's default date. Between 20:00 and midnight in Dubai that returns yesterday, so an EOD report run at 20:30 — exactly when somebody would run it — would have summarised the wrong day entirely.

New packages/core/src/time.ts: localTime, localDateTime, localDate, companyToday, all Asia/Dubai. Anything calling toISOString() on a user-facing path is now a bug.

Built for scale

bot.start() processes updates one at a time. Every handler here can make a model call taking 1-4 seconds, so ten employees reporting at the end of a shift queue behind each other and the tenth waits the better part of a minute — for a bot whose entire value proposition is that reporting is quick.

1 · Concurrent processing, sequential per person

Moved to @grammyjs/runner, with sequentialize() keyed by chat id as the first middleware, ahead of session loading.

The sequencing is not optional. Conversation state lives in one bot_session row per chat: two concurrent handlers for the same person would both read the same step, both act on it, and the later write would erase the earlier — losing a half-finished registration, or creating one document's tasks twice. Different people run in parallel; one person runs in order.

sink.concurrency is 50, far below the runner's default of 500 — this box has 8 vCPU shared with Postgres, Redis and the worker, and admitting more work than can be served converts a queue into memory pressure.

2 · The cap belongs at the model, not the bot

Processing updates concurrently does not make a system scale; it moves the bottleneck. Ten simultaneous messages become ten simultaneous model calls, and the provider answers with 429s.

llmSemaphore (6 concurrent, 200 queued) wraps llmComplete — which every model call in the system already funnels through, so the cap is honest rather than advisory. Documents get their own narrower semaphore (2), because a document read is a download plus a parse plus a large prompt.

The wait queue is bounded. An unbounded queue under sustained overload is a slower way to run out of memory, and it holds work until long after the person gave up. Past the cap we fail fast and say so. Waiting is the right behaviour otherwise: an employee whose message takes four seconds instead of two still gets an answer, whereas one whose message is dropped has learned not to trust the bot.

3 · Measured, not assumed

20 simultaneous messages through the real pipeline

elapsed        : 8161ms
succeeded      : 20/20
failed         : 0
peak concurrent: 6   (exactly the limit)
peak queued    : 14
rejected       : 0
throughput     : 2.5 msg/sec

sequential would have taken roughly 30s  →  about 3.7x

4 · Saturation is observable

/health now reports load per semaphore — active, waiting, peak, rejected — and returns busy when anyone is queuing. waiting above zero means people are queuing for a model slot; rejected above zero is the number that says the box needs more capacity rather than more patience.

A regression I introduced and fixed

While switching to the runner I called bot.api.getMe() outside the retry wrapper, purely to print the username in a log line. A routine ECONNRESET on this link — which happens several times an hour here — killed the process before it ever polled. Caught immediately because the restart failed loudly. Anything touching the network at startup now goes through withRetry, including calls whose only purpose is a log line, and an unhandledRejection handler keeps a transient fault from taking the bot down silently.

Verification

  • Bot confirmed running: @freshnow1bot polling concurrently (sink 50, per-chat sequential, 6 concurrent model calls).
  • /health confirmed returning live load figures.

What we have not verified

  • The limits are reasoned, not measured against a real workforce. 6 concurrent model calls, 2 documents, sink 50 — chosen from this box's shape. They should be revisited once real load exists; there is no evidence yet about where this box actually degrades.
  • No test has exceeded 20 concurrent messages. The queue cap and the QueueFullError path are covered by unit tests only, never live.
  • No soak test. The runner has not been observed under sustained multi-hour load, so nothing is known about memory behaviour over time.
  • Per-chat sequencing is verified by construction — grammY's guarantee plus middleware order — not by a live race test. A test that fires two updates for one chat and asserts the session survives would be worth writing.
  • The worker is still a single process polling the outbox every 3s. That is fine at this volume but is the next thing to hit a ceiling, and it has not been load-tested at all.
  • Postgres pool is 5 connections per role. Not tuned against the new concurrency, and not yet a measured constraint.
  • Carried over: voice accuracy unmeasured; llm_call.cost_usd reports 0; the NL-query box still runs as the service role rather than under the viewer's RLS context.
