TASK-005 — Outbox Worker

Phase 1 (demo) · 2026-09-04 · Satisfies SPEC-000 R24 (loss of Telegram must not lose a notification) and the "outbox pattern for every outbound message" rule · A transactional outbox relay with idempotent, at-least-once delivery. 34/34 tests green.

What was done

  • packages/core/src/outbox.ts — enqueueNotification(): inserts a row with ON CONFLICT (idempotency_key) DO NOTHING, so a duplicate enqueue is a no-op.
  • packages/worker/src/outbox-relay.ts — deliverOutboxBatch(deliver): claims pending rows with FOR UPDATE SKIP LOCKED, delivers each, marks sent; a hard failure retries up to maxAttempts then abandoned; a RateLimitError (429) leaves the row pending and never abandons.
  • telegram-sender.ts — the real Telegram sendMessage deliverer (maps 429 → RateLimitError); injected at runtime, stubbed in tests.
  • worker/src/index.ts — the poll loop.
  • 5 tests against the real DB with a stub deliverer: delivers+marks sent, idempotent enqueue, no re-delivery of a sent row, abandon-after-max, and 429-stays-pending.

Why it was done

Never call Telegram from business logic. A handler that sends directly loses the message if Telegram is momentarily down, and can double-send on a retry. Writing a row and letting one worker deliver it makes delivery survive restarts and be exactly-once from the recipient's point of view (the idempotency_key guarantees one logical message is enqueued once).

SKIP LOCKED for safe concurrency. Multiple workers can poll at once; each locks a disjoint batch, so no message is delivered twice by racing workers.

How it works

business logic ─▶ enqueueNotification({idempotencyKey, chatId, payload})
                    insert … on conflict (idempotency_key) do nothing   ← dedupe at enqueue

worker poll (every ~3s):
  BEGIN
    select … from notification_outbox
      where status='pending' order by created_at
      limit N FOR UPDATE SKIP LOCKED           ← claim a batch, skip locked rows
    for each row:
       deliver(row)                            ← Telegram sendMessage
         ok        → status='sent', sent_at=now()
         429       → leave 'pending' (retry later), never abandon
         error     → attempts++ ; ≥max → 'abandoned' else stay 'pending'
  COMMIT

Concepts and techniques used

  • Transactional outbox — outbound intent is a database row; a relay delivers it, decoupling the write from the send.
  • FOR UPDATE SKIP LOCKED — lock-free-ish batch claiming so parallel workers never double-deliver.
  • Idempotency key + at-least-once — the outbox guarantees at-least-once; the UNIQUE key makes the recipient see one logical message. Consumers (Telegram) are treated as idempotent-enough at demo volume.
  • Injectable deliverer — the relay takes a Deliverer function, so tests use a stub and no bot token is needed to prove the mechanics.
  • Rate-limit backoff — a 429 is a distinct error that pauses, never abandons.

Research findings

Reviewed the transactional-outbox pattern (multiple 2025–2026 write-ups). Key confirmations: the pattern is at-least-once, not exactly-once — if the relay delivers then crashes before marking sent, it re-delivers on restart, so consumers must tolerate a duplicate; and SKIP LOCKED is the standard mechanism for multi-worker claiming.

Deviation from the task-board wording. The board said "Outbox worker: BullMQ". The canonical, more reliable implementation here is a DB-polling relay with SKIP LOCKED (which the system blueprint's own timeline describes). BullMQ + Redis is reserved for what it is genuinely best at — delayed SLA/escalation jobs (Task 009). Recorded as decision D14.

What we have not verified

  • No real Telegram delivery yet — telegram-sender.ts is unexercised because no BOT_TOKEN has been supplied. Tests use a stub deliverer.
  • Delivery happens inside the DB transaction, holding the row lock during the HTTP call. Fine at demo volume; for scale, claim-then-deliver outside the lock (needs a sending status + a stale-row reaper).
  • Double-send on crash (deliver succeeds, worker dies before COMMIT) is possible — at-least-once by design. Not reproduced or measured.
  • Real 429 handling has not been observed against live Telegram, only simulated.
  • Throughput / backpressure under many pending rows is untested.
