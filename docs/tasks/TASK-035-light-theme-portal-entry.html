TASK-035 — A light theme, and the portal picker before the password

2026-09-18 · dashboard only · index.css two-palette tokens · lib/theme.ts · Root.tsx rewritten · 26 hardcoded colours removed · 23 + 8 browser checks · 321 tests still green

One-sentence summary: The dashboard now opens on a choice of the two portals before asking for a password and lands you in the one you picked; and it has a real light theme — every colour is a token with two values, an explicit choice beats the operating system, and both themes were measured to pass WCAG AA on real data rather than eyeballed.

1 · The entry flow

Before: sign in, then discover a portal switch in the header. After: choose a portal, sign in, work.

  open /app/  →  ┌ Task & logging ┐  ┌ Projects ┐   ← no password asked yet
                 └────────┬───────┘  └────┬─────┘
                          └─────┬─────────┘
                    "Sign in to <portal>"  →  that portal's dashboard
                                                (header still switches between them)

Choosing first is worth the extra click because the two portals answer different questions, a person usually arrives already knowing which one they came for, and the sign-in screen can then say what you are signing in to. Signing out returns to the picker rather than to a bare login box.

What the picker is not

It is not a security boundary, and the UI says so. The same account opens both portals; what a person may see or do is decided by their role and by row-level security in Postgres, exactly as before. The login card carries the line "One account opens both portals — what you can see and do is set by your role."

This mattered enough to write down. A picker that looks like two separate logins would imply a boundary that does not exist, and a person who believes the Projects portal is walled off from the task data would be wrong in a way the interface had encouraged. Implying a boundary that is not enforced is worse than having none.

An existing session is not re-challenged. Somebody who is already signed in picks a portal and goes straight in. Asking again for a password the browser is already holding is theatre, not security.

2 · The light theme

DecisionWhy
Every colour is a token with two values, dark declared in @theme and light overriding the same names under :root[data-theme="light"].No component knows which theme is on. It asks for bg-panel and gets whatever the root says, so a third theme later is a block of CSS and no component changes.
All 26 hardcoded hex literals were removed first. bg-[#1f2630] → bg-sunken, and so on.This is the whole job. A literal is invisible in dark and a black hole in light — the theme cannot work while any survive. New tokens: sunken, well, on-accent, the three severity pairs, demo-edge, scrim.
Three states, not a switch: Light · Dark · Auto.A two-state toggle cannot express "it is dark because my laptop is". Auto tracks the OS live — change the system theme with the page open and it follows — and an explicit choice beats it and persists.
The theme is applied before React mounts, by an inline script in index.html.Anything deferred runs after the browser has already painted, so a light-theme reload would flash dark first. It has to be inline and synchronous.
color-scheme is set per theme.The native date picker in the header, scrollbars and form controls are drawn by the browser, not by our CSS — without this they stay dark on a light page. It is the one part of the UI CSS cannot reach.
The light accents are darker than GitHub's own.Measured, not preferred: these are 14px text on their own 15% tint (the selected tab, the active nav item). GitHub's values are fine on white (≈5.1:1) but reach only ≈4.15:1 on that tint — under AA. Darkening gives ≈5.9:1 on the tint, ≈7.4:1 on white.

The measurement was wrong twice before it was right

Worth recording, because the wrong version was persuasive. The first contrast check treated a bg-ok/15 tint as a solid fill — it only walked up the tree when a background was fully transparent. That produced a plausible-looking 4.13:1, which I acted on; then, after darkening the palette, the same broken check reported 2.84:1 — worse, which is what exposed it.

Rewritten to composite alpha properly over every ancestor, it reports zero failures. Recomputing the numbers by hand afterwards showed the darkening had been justified anyway (4.14 → 5.84 on the tint) — but that was luck, not method. A measurement you have not sanity-checked is worse than no measurement, because you will act on it.

What we have not verified

  • Demo mode (authRequired: false) was not exercised. The API currently runs with sign-in on. The path is short — picker, then App with no identity — and typechecks, but it was reasoned about rather than run.
  • No phone, no projector. Everything was checked in headless Edge at 1280–1400px. The light theme's actual purpose — a bright room — has never been seen in one, and the toggle has not been tapped on a phone.
  • Contrast was measured on the pages the check visits (Carry-over, Activity, Alerts, People, a task drawer, the picker, the login card). The Projects portal's inner sections, the Ask tab and the document-upload card were not measured, only looked at.
  • AA, not AAA, and non-text contrast (borders, the progress-bar fills, focus rings) was not measured at all — only text.
  • The older scratchpad browser harnesses now start at the picker and would need a portal click added. They are throwaway checks, not part of pnpm test, so nothing in CI is affected.
  • No automated test guards the theme. The browser checks are scratchpad scripts; a future change that reintroduces a hex literal would not fail pnpm test. A lint rule banning [# in className would close that, and was not added.
