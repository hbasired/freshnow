🌐 How it actually connects

Telegram messages never touch your local network. This is the part that surprises people, and it is worth understanding before the demo.

   CEO phone                Telegram servers               Your PC
  (any network)             (api.telegram.org)          (bot process)
       |                            |                         |
       |  1. "/invite Hemanth"      |                         |
       |--------------------------->|                         |
       |                            |<------------------------|
       |                            |  2. bot asks over HTTPS:
       |                            |     "anything new?"  (getUpdates)
       |                            |     -- OUTBOUND, held open --
       |                            |------------------------>|
       |                            |  3. Telegram hands over the message
       |                            |                         |
       |                            |                4. bot writes to Postgres
       |                            |                   on localhost:5433
       |                            |<------------------------|
       |                            |  5. sendMessage (OUTBOUND HTTPS)
       |<---------------------------|                         |
       |  6. the code appears       |                         |
The key point. Your PC never receives an incoming connection. It only makes outbound HTTPS calls to api.telegram.org. That is why this works behind a home router with no port forwarding, no public IP, and no firewall changes. This is called long polling.

How the invite code is verified

Nothing is "sent to your PC" by the employee. The sequence is:

1
Employee types the code in Telegram → it reaches Telegram's servers.
2
Your bot picks it up on its next getUpdates poll (~1 second).
3
validateInvite(code) runs a local SQL SELECT: does this code exist, is it unredeemed, is it unexpired?
4
If valid, the consent notice is shown. The code is not consumed yet — consent comes first.
5
On "I agree", redeemInvite() runs one transaction with the invite row locked (SELECT … FOR UPDATE): creates the employee row carrying their Telegram user id, marks the invite_code redeemed, and writes the consent_record. All three succeed together or none do — so a double redeem can never create two identities.
The employee's Telegram ID is captured automatically at step 5. Nobody types it, and the CEO never needs it.

What actually goes to the AI — and what does not

A common assumption is "every message goes to the AI". It does not, and that matters for cost, speed and reliability.

What happensTouches Groq?Why
Tapping ✅ Done / ⏳ Pending / 🚫 BlockerNoThe tap is the status. Recorded directly.
Entering an invite codeNoPlain SQL: does it exist, unused, unexpired?
The 4 registration answersNoWritten straight to columns.
Free text describing a problemYesWords → {category, severity, summary}
A voice noteYes, twiceWhisper transcribes → then the text is parsed
Deciding who fixes itNoA table lookup in routing_rule
Deciding whether to escalateNoA rule on severity + age + SLA
The last two are the important ones. Once the AI has said what kind of problem it is, it stops. Who it goes to and whether it escalates are decided by Postgres — which is why "why did this go to X?" is answerable by pointing at a row, and why the same input always produces the same decision.

The exact order when someone reports a problem

The storage order is the opposite of what people usually assume — the words are saved before the AI is called, not after:

1. employee's words arrive
2. WRITE RAW TEXT TO POSTGRES        <-- first, always
3. reply "saved" to the employee     <-- they are free to go
4. send the text to Groq             <-- may be slow, may fail
5. write the parsed result back
6. look up the resolver (SQL, no AI)
7. queue the CEO alert in notification_outbox
8. worker delivers it via an outbound call to Telegram
If Groq is down at step 4, steps 1–3 already happened: the employee's exact words are safe, they were told it was received, and the update is flagged for a human instead. Nothing is ever lost because the AI was unavailable.

What changes when you deploy to the VPS

The application code does not change. Only the transport flips:

Demo (now)VPS (production)
How Telegram reaches the botLong polling — bot asks TelegramWebhook — Telegram pushes to you
Needs a public addressNoYes — a domain, e.g. ops.freshnow.ae
Needs TLSNoYes — Caddy issues it automatically
Security checkn/aVerify X-Telegram-Bot-Api-Secret-Token on every request
Dashboard reached atLAN IP, same wifihttps://ops.freshnow.ae from anywhere
Set byTELEGRAM_MODE=pollingTELEGRAM_MODE=webhook + TELEGRAM_WEBHOOK_URL + TELEGRAM_WEBHOOK_SECRET

Why webhook in production: polling wastes requests and adds a second of latency; webhooks are pushed instantly. Why polling now: a webhook needs a public HTTPS URL, which a laptop on wifi does not have.

One trap for later: if you ever point the webhook at a dev tunnel and forget to reset it, production silently stops receiving messages. getWebhookInfo tells you where the webhook currently points.

⭐ The one thing to understand

The CEO does NOT need the employee's Telegram ID to create an invite code. A code is created from a name only. The ID is captured automatically when they redeem it. 
CEO creates a code (from a name)  →  gives the code to the person  →  person enters it
You can create every code before the demo starts.
❌ What does NOT work. A new person sending "here are my details + my unique ID" as a message. The bot replies "Send /start to see your menu" and nothing is created.

That is deliberate: identity is never self-declared, otherwise anyone who finds the bot could enrol as staff. The invite code is the authorisation gate. After the gate, the bot asks 4 questions one at a time — they do not send a block of text.

The three killer points for officials

1. "Why did this go to X?" — the answer is a row in routing_rule, not a model's opinion. Same input, same decision, every time.
2. Nothing is ever lost. The employee's exact words are saved before the AI is called. If the AI is down, the words survive and a human is told.
3. Every number is traceable. Everything shares a correlation id, so any figure traces back to the exact message and rule that produced it.

Be honest about these if asked

  • Existing employees and blockers are synthetic, badged DEMO DATA. Anyone who registers today is real and unbadged.
  • Routing goes to the CEO only — the table is real and deterministic, but every category points at the CEO because FreshNow has not supplied the real resolver map. Changing it later is a data change, not a rewrite.
  • Blocker categories and SLA windows are placeholders, not FreshNow's real ones.
  • The Hindi and Malayalam privacy notices have not been checked by a native speaker.
  • The NVIDIA fallback model is failing (503). Groq does all the work; if Groq is down, updates are saved and flagged for a human rather than parsed.
  • Voice accuracy on real speech is unmeasured — the pipeline is verified, the accuracy is not.
